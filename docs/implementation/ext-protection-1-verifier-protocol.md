# EXT-PROTECTION-1 owner verifier protocol

This is the protocol implemented by `tools/verify-ext-protection-1.py`. It is a qualification harness, not a custody provider or an independently installed observer. The owner acceptance packet records outstanding installation and qualification requirements. Source mode and offline unit tests do not execute Live.

From the Agents repository root, the proposed entry point is:

```bash
python3 ../eventstore/tools/verify-ext-protection-1.py --mode Live --profile /home/administrator/hexalith-protection-evidence/ext-protection-1/accepted-profile.json --evidence-root /home/administrator/hexalith-protection-evidence/ext-protection-1/attempts
```

Do not execute this command before owner-record acceptance. It reads the Agents register, requires EXT-PROTECTION-1 `Committed` or `Available`, validates its accepted ISO integration date without requiring a particular literal date, and requires exact clean EventStore and Platform checkouts with ancestry from their local `origin/main` refs. It does not fetch or alter Git state. The accepted compatibility field must bind the installed profile with `ProtectionProfileSha256=` followed by its exact SHA-256 and the full Platform commit with `ProtectionPlatformTargetCommit=` followed by 40 lowercase hexadecimal digits. These belong in the existing compatibility field, not new register rows. Both commits and the role-program contract participate in the retained binding digest and exact-original recovery identity. Older profiles lacking the Platform pin fail closed. The command has a success branch after all installed inputs and every case pass; current input absence is not converted to availability.

Each invocation creates a fresh retained UTC/UUID attempt directory, including refusals. No file is overwritten or cleaned. The `binding.json` identity contains exact target/profile/plan/anchor hashes. The independent enrollment role must durably enforce one attempt per accepted target set across machines and evidence roots. A local directory alone does not establish that policy.

## Installed profile

The profile is a JSON object with exactly these members:

| Member | Value |
| --- | --- |
| `schema` | `ext-protection-1-profile/v2` |
| `targetCommit` | Accepted full EventStore commit |
| `platformTargetCommit` | Accepted full Platform commit equal to the compatibility field's `ProtectionPlatformTargetCommit` pin |
| `platformRoot` | Absolute path of the separate exact clean Platform checkout; checked before any role invocation |
| `roleProgramContract` | Exactly `ext-protection-1-role-program/v1`, the stdin/stdout role transport below |
| `planSha256` | SHA-256 of exact committed `tools/ext-protection-1/plan.json` bytes |
| `tenantReferences` | Object containing distinct nonempty `primary` and `other` tenant references |
| `roles` | Object containing exactly `executor`, `observer`, `enrollment` |
| `engineBinary` | Object containing absolute installed `path` and exact `sha256` |
| `capabilityTrust` | Nonempty array of the separate accepted deletion-capability trust records below; at most 1,000 |

Each role contains exactly `executable`, `executableSha256`, `publicAnchorFile`, `publicAnchorSha256`, `credentialReference`, `identity`, `installationManifest`, `installationManifestSha256`. Paths are absolute reference-only inputs, credentials are `env:NAME` references, and anchors are public P-256 PEM keys. No private signing material, KEK, DEK, bearer value, plaintext domain content, or connection string belongs in this file. Each installation manifest is a hash-bound object with `files`, an array of exact `{path, sha256}` objects including the executable and its complete installed dependency inventory. The entire inventory, manifest, executable, anchor and engine binary are checked before each role call. Distinct role identities, credential references and actual public-key fingerprints are mandatory. A role process receives only its own referenced credential plus a fixed PATH and locale; it does not inherit the other roles' credentials.

Every `capabilityTrust` entry has exactly `issuer`, `audience`, `tenantId`, `keyFamily`, `keyVersion`, `publicAnchorId`, `publicAnchorVersion`, `publicAnchorFile`, `publicAnchorSha256`, and `trustProfileRevision`. All except the revision are nonempty strings. The revision is a positive exact JSON integer no larger than 9,007,199,254,740,991. `keyFamily` is exactly `DeletionBatchCapabilitySigningKey`; `tenantId` must be one of the profile's tenant references. Issuer/audience/tenant/family/version tuples must be unique. The file is an absolute public P-256 PEM reference and its SHA-256 is lowercase hexadecimal. Its actual public-key fingerprint must differ from every transport-role key and cannot be reused by another tenant, even if the same key is encoded differently. All capability anchors and all three transport anchors are rechecked before **every** role invocation, including recovery calls. A missing or changed accepted anchor blocks the invocation. The accepted profile hash already participates in `bindingDigest`, so adding or changing trust requires acceptance of a new exact profile hash.

Public keys are normalized to uncompressed P-256 DER before fingerprint comparison; compressed/uncompressed PEM encodings cannot bypass role or tenant separation. Public anchor files are bounded to 16 KiB. Each observation is bounded to 16 MiB and one 30-second monotonic verification budget, including public-key parsing, signature subprocesses, native correlation, and final pin rechecks. At its boundary the verifier captures hash-checked immutable public bytes and indexes accepted trust once; each distinct public file is parsed once and each identical signed payload/JWS is verified once within that observation. Signature verification uses a temporary copy of those captured public bytes, never a reopened mutable installed anchor. It rechecks every accepted public pin at the end of the observation and before every later role call. This bounds work to the trust inventory plus distinct signed requests, rather than multiplying a full trust scan by every request. Deadline exhaustion blocks validation.

Old capability-key versions remain separate trust entries through retained batch/outcome lifetimes. There is no capability expiry, renewal, current-key shortcut, or generated installation. Profile/v1 is rejected. These public references do not install signing authority or establish revocation currentness.

The enrollment authority must independently bind store/deployment identity, role principals/ACLs, installation inventories, engine binary/source identity, contract/plan hashes, and the isolated fixture namespace. It cannot be the executor or observer. The observer must read actual persisted source/event/snapshot/cache/backup/key/provider and protection/guard records under its separate read-only credential. It must not accept executor-supplied state, response codes, booleans or mock call counts as a persisted observation. No Agents package or consuming runtime path may be involved. These independently operated installations do not currently exist in this workspace.

## Role transport

The verifier launches the pinned executable directly, without a shell or secret argv. It writes one canonical UTF-8 JSON request to stdin. Every request carries `operationId`, `action`, `bindingDigest` and action-specific exact identities. A role writes one object containing exactly `statement` and `signature`. `signature` is base64 IEEE-P1363 ES256 over the canonical JSON statement (sorted member names, compact separators, UTF-8, finite JSON). `statement` contains exactly `role`, `identity`, `bindingDigest`, `operationId`, `requestSha256`, `response`. Fresh request ids prevent replay of stale observations; signatures bind the exact complete request digest.

`InspectInstallation` precedes enrollment or fixture mutations. It returns installed engine/source/binary/store/deployment identities, disabled Agents consumers, supported operations, and observer read-only ACL scope. All three roles must name the same store and deployment, which are bound into enrollment. `EnrollSingleAttempt` returns the exact attempt and binding identities with status `Enrolled`; repeat/lost enrollment is resolved by exact original lookup.

The 41-case plan owns the operations and assertions. `PrepareFixture` creates an isolated deterministic namespace and complete target cohort; all `Seal*` operations apply the synthetic canary to the requested targets. They must use the shipped hooks and original actor commit paths. Other operations invoke actual named custody/guard/protection APIs, inject the specified boundary condition, or control the explicit race schedule. Race drivers may coordinate operation arrival but cannot decide the verifier result. No production domain content is used.

`ObservePersistedState` is separately signed and includes the exact requested operation identity/digest/action vector plus persisted `roots`, sealed `records`, loaded engine identity, disabled-consumer state, and the case-specific receipts/guard transitions/copy inventories checked in `evaluate`. Field names and required checks are executable in `tools/ext_protection_1.py`; incomplete observations fail. `Unseal*` returns `canaryBase64` for in-memory equality comparison only. Its plaintext response is not retained.

## Capability and original receipt observations

For a `capability` or `receipts` assertion, the observation supplies `consumptionRequests`, `guardBatches`, and `guardReceipts`. Naked `capabilities`, `guardDispatch.soleActiveAttestation`, and `lookupConsistency` labels supply no authority. When `consumptionRequests` is present in another case, it is validated too. Each array contains JSON objects using the exact native C# member names, with no unknown members:

| Array | Exact object members |
| --- | --- |
| `consumptionRequests` | `Capability`, `DetachedJws`, `CommittedIssuedGuardRevision`, `DispatchReceiptId`, `DispatchGuardRevision`, `Targets` |
| `guardBatches` | `BatchId`, `Kind`, `Ordinal`, `Targets`, `ManifestDigest`, `AttestationOrdinal`, `CapabilityKeyVersion`, `AttestationDigest`, `IssueReceiptId`, `DispatchReceiptId`, `ProtectionOutcome`, `ProtectionReceiptId`, `TargetReceiptIds`, `BlockSetRevision`, `CoveredResourceIds`, `Capability`, `DetachedJws`, `SigningRequestId`, `IssuedGuardRevision`, `DispatchGuardRevision` |
| `guardReceipts` | `OperationId`, `IntentDigest`, `Status`, `GuardHighWater`, `AcceptedAtAdmissionFenceOrdinal`, `ReferenceId`, `ReceiptId`, `AdmissionAttributionsJson`, `AcceptedWriteResourceId`, `AcceptedWriteFacts`, `AcceptedTargetMutationDigest`, `Capability`, `SigningRequestId`, `DetachedJwsDigest` |

`Capability` is the closed fourteen-field `DeletionBatchCapabilityV1`: `Issuer`, `Audience`, `TenantId`, `DeletionRequestId`, `DestructionSealId`, `BatchKind`, `BatchOrdinal`, `BatchId`, `ManifestDigest`, `GuardStreamId`, `IntendedIssuedGuardRevision`, `AttestationOrdinal`, `SigningAttemptOrdinal`, and `CapabilityKeyVersion`. The four ordinal/revision payload members must be exact integers at most 9,007,199,254,740,991; `BatchOrdinal` can be zero and the other three must be positive. Booleans and fractions are rejected. Strings must be nonblank valid Unicode within the native identity bounds (2,048 UTF-16 code units and 2,048 UTF-8 bytes for consumption identities). Duplicate JSON members are rejected throughout role envelopes and installed input files.

Native `DeletionConsumptionIdentity.Capture` also constructs `AggregateIdentity(TenantId, "protection", BatchId)`: the tenant lowercases for validation and is then limited to 64 ASCII alphanumeric/hyphen characters with alphanumeric ends; batch id is at most 256 ASCII alphanumeric/dot/hyphen/underscore characters with alphanumeric ends. Capture retains the original request tenant, so uppercase ASCII tenants are accepted unchanged. Unicode remains valid in permitted alias, interaction, issuer/audience, deletion-request, seal, and guard fields. Dispatch ids, owner/provider reservation ids, per-target receipt ids, and original batch identities obey their native 2,048-byte bounds. Successful issue/dispatch and owner/block-set revisions are typed native nonnegative/positive signed 64-bit integers as appropriate; the stricter exact-integer bound above applies to the signed payload.

Signed payload bytes follow `DeletionBatchCapabilityIdentity.CanonicalPayload`: sorted closed field names, compact RFC8785 string/integer serialization, preserved Unicode without normalization, and no final newline. The deterministic `SigningRequestId` is uppercase SHA-256 of those bytes. `Targets` is a bounded nonempty list (at most 1,000), each with exactly `TenantId`, `AgentInteractionId`, and `TargetProtectionKeyAlias`. Every target has the capability's tenant. Targets are strictly sorted by interaction then alias using .NET ordinal UTF-16 ordering; duplicates fail. `ManifestDigest` is uppercase SHA-256 of the default **System.Text.Json** serialized ordered string arrays `[TenantId, AgentInteractionId, TargetProtectionKeyAlias]`. This uses the native HTML/Unicode escaping and differs from the capability's RFC8785 bytes. The request cohort covers the complete expected target inventory exactly once; containment requests have a positive ordinal and one target, accepted-set requests have ordinal zero.

Exactly one accepted trust entry must match issuer/audience/tenant/key version. Its protected header is the exact canonical JSON object with `alg: "ES256"`, `anchorVersion`, `keyVersion`, `kid` (public anchor id), and `typ: "DeletionBatchCapabilityV1"`. The detached form is `base64url(header)..base64url(signature)`; the signature is 64-byte P1363 P-256/SHA-256 over `base64url(header).base64url(canonical payload)`. Both segments must be unpadded canonical base64url. Attached payloads, duplicate/unknown/reordered/noncanonical headers, changed anchors, and any signed-identity substitution reject.

There must be one unambiguous retained `GovernanceBatchState` per request. Its exact capability, detached signature, signing request id, signature digest, targets, batch kind/ordinal, manifest, attestation, and key version must agree. Native `AttestationDigest` and receipt `DetachedJwsDigest` are uppercase SHA-256 of the original detached JWS UTF-8 bytes. The batch's `IssueReceiptId` and `DispatchReceiptId` select distinct original `GovernanceProtocolReceipt` records with different operation ids, `Status: "Committed"`, the exact batch `ReferenceId`, the same original capability/signing id/signature digest, and the exact successful `GuardHighWater`. Actual issue is the signed intended revision plus one; actual dispatch follows issue. Request `CommittedIssuedGuardRevision` matches batch `IssuedGuardRevision`; both dispatch revisions and the dispatch receipt id match. The native receipt has no separate issue/dispatch revision or operation-type member: those are correlated through the batch and `GuardHighWater`, without inventing fields. This detects inconsistent originals; it does not prove that a snapshot is the current sole unrevoked attestation or that its read was linearizable.

Retained capability comparisons validate and compare their canonical native bytes, so Python equality cannot admit booleans/floats in place of integers. Referenced issue/dispatch originals are also indexed by `(GuardStreamId, OperationId)` across the complete signed cohort; a conflicting receipt at one operation identity rejects. `BlockSetRevision` is a typed nonnegative native integer. The cohort must cover the full expected target inventory exactly once, including when several signed singleton containment requests form the cohort.

For a `receipts` assertion, the following additional arrays are mandatory:

| Array | Native record / exact members |
| --- | --- |
| `ownerResults`, `ownerRetryResults`, `ownerLookupResults` | `DeletionConsumptionOutcome`: `TenantId`, `BatchId`, `Status`, `OwnerRevision`, `KeyBlockSetRevision`, `ReceiptId`, `BlockReason`, `BlockedKeyVersion`, `RevocationRevision`, `TargetReceipts` |
| `providerResults`, `providerLookupResults` | `DeletionManifestProviderResult`: `TenantId`, `BatchId`, `ReservationReceiptId`, `State`, `TargetReceipts` |
| Every `TargetReceipts` item | `DeletionTargetReceipt`: `Target`, `OriginalBatchId`, `ReceiptId` |
| `ownerBatches` | Actual persisted private `DeletionConsumptionBatch`: `Original`, `Current`, `Outcome`, `BlockedReplacement` |

Enums use native default System.Text.Json numeric values: owner `Status: 3` is `Consumed`, provider `State: 1` is `Consumed`, and coverage owner `Status: 4` is `AlreadyDestroyedByBatch`. There is one consumed owner and provider original per request. Tenant/batch must match, owner revision is positive, block-set revision is nonnegative and cannot exceed owner revision, the consumed outcome has null block fields, and provider reservation equals the owner `ReceiptId`. Both vectors must contain the complete ordered request targets, each with the consuming batch as `OriginalBatchId` and a distinct nonempty original `ReceiptId`; vectors must match exactly across owner and provider. Every consumed observation requires the guard's consistent `Consumed` terminal mirror with that owner receipt and target receipt id vector; a stale `Unconsumed` or replacement-awaiting state cannot qualify a consumed case. The guard's block-set revision cannot exceed the owner outcome's block-set revision. Every request also requires at least one owner retry, owner lookup, and provider lookup original. Each must equal the corresponding **complete** original native record under canonical JSON comparison, including its vector and revisions. `exact-results` always additionally compares its operation-specific `exactResults`, including P36 activation results even when consumption receipts also pass. No `irreversible: true` field is accepted or used. This establishes offline record consistency, not physical irreversibility or provider authenticity.

`ownerBatches` is required from the actual persisted owner state, with one record per consumed request (plus the retained coverage record when coverage is asserted). `Current` is the complete native `DeletionBatchConsumptionRequest` and must equal the independently signed consumption request under canonical comparison. `Outcome` must equal the complete consumed owner original, binding the provider's reservation and vector to that persisted exact request. `BlockedReplacement` must be null for these terminal records. `Original` remains a complete retained native request: its old signature is verified against retained trust, its immutable tenant/issuer/audience/deletion request/seal/kind/ordinal/batch/manifest/guard/targets must match `Current`, and its attestation ordinal cannot exceed `Current`. When the attestation ordinal is unchanged, the exact original request must be unchanged. This reads the existing private record; it introduces no public reservation API.

`coverageOutcome`, when asserted, is a complete native `DeletionConsumptionOutcome` with `AlreadyDestroyedByBatch`, a bounded string later batch id, and the unchanged original ordered receipt vector. `coverageRequest` is the complete actual supplied native `DeletionBatchConsumptionRequest`, including its retained public artifact; its batch/tenant must match that outcome and its complete ordered targets must match the original covered targets. Its retained `ownerBatches` record binds the same exact `Current`/`Outcome`, with immutable `Original` identity. Coverage uses native Capture validation to bind the supplied request and does not require minting a new signature, ordinal, capability, or successor authority. Its per-target `OriginalBatchId` continues to identify the earlier consuming batch. This is defense-in-depth exact coverage, never permission for a new effect. When hold-order, pin, coverage, re-attestation, replacement-blocked activation, or restore is asserted, the matching native original must be present and agree with the summary: `guardReceipts` for hold order, `pinOriginals` for pin, `coverageOriginals` for coverage, `activationOriginal` for re-attestation and replacement-blocked activation, and `restoreOriginals` for restore. A substituted, missing, ambiguous, or schema-invalid original rejects. P39 also requires the native signing and intent originals described below; a signing summary alone is rejected. These offline comparisons do not reconstruct an installed append chain or prove a linearizable online read.

Offline byte/signature vectors are retained in `tools/tests/fixtures/ext-protection-1/capability-vectors.json`. The separate `test_ext_protection_1_cross_language.py` builds a temporary probe referencing the real EventStore Contracts project and linking the actual Platform byte codec and native `DeletionConsumptionIdentity` source, then verifies canonical/manifest bytes, ES256 signatures in both directions, and actual native Capture acceptance/rejection. Cases include uppercase tenants, 64/65-character tenant and 256/257-character batch limits, Unicode tenant rejection, and 2,048-byte identity limits while retaining Unicode/HTML codec vectors in permitted fields. It prefers the root-declared `references/Hexalith.Platform` source and permits the sibling Platform checkout as a fallback; it never initializes submodules. Local defaults are Debug and `UseHexalithProjectReferences=true`. The existing offline CI lane selects both test modules with `EXT_PROTECTION_INTEROP_CONFIGURATION=Release` and `EXT_PROTECTION_INTEROP_PROJECT_REFERENCES=false`, preserving Release/package dependency references. Its keys exist only in a temporary offline test directory. It invokes no installed role, Live mode, or cohort.

## Native signing and no-issue originals

P39 (`signing-attempts`) requires at least three consecutive attempts for one immutable logical capability. Every attempt retains issuer, audience, tenant, deletion request, seal, batch kind/ordinal/id, manifest, guard stream and attestation. Only the consecutive signing-attempt ordinal, successor intended guard revision and current healthy key version may change. These arrays are mandatory and bounded by the same 16 MiB observation and thirty-second verification budget:

| Observation | Required original |
| --- | --- |
| `signingAttempts` | Closed summaries: `DestructionSealId`, `BatchId`, `ManifestDigest`, `AttestationOrdinal`, `SigningAttemptOrdinal`, `status`, `exactNoIssueReceiptId`. The final status is `Signed` with a null no-issue id; predecessors are `SignedAttestationObsoleteUnissued`. |
| `signingOriginals` | One actual `DeletionCapabilitySigningOutcome` per summary: `SigningRequestId`, complete `Payload`, numeric `State`, original `DetachedJws`, `PublicAnchorId`, `PublicAnchorVersion`, and the retained `NoIssueProof` for obsolete outcomes. Native states are `5` for obsolete/unissued and `0` for Signed. A final null `NoIssueProof` may be omitted by native serialization. |
| `noIssueOriginals` | One complete native `GovernanceProtocolReceipt` per obsolete attempt, with the exact stale or `IssuanceStale` result. `Stale` has empty `ReferenceId` and zero admission ordinal; `IssuanceStale` names the original BatchId and a positive deletion ordinal. |
| `signingRecoveries` | One actual `GovernanceSigningRecovery` per obsolete attempt. It retains the same payload, signing id, detached-JWS digest and `NoIssueReceiptId`, and supplies the successor's exact intended guard revision and healthy key version. |
| `noIssueIntents` | One closed `{BytesBase64}` object per obsolete attempt. Its canonical base64 decodes to the actual retained native serialized `{Transition,TargetMutationDigest}` intent original used by `GovernanceScopeGuardOwner`; it is not constructed from a receipt summary. |

A `NoIssueProof` contains exactly `Payload`, `SigningRequestId`, `DetachedJwsDigest`, `ProofId`, `CurrentGuardRevision`, `CurrentHealthyKeyVersion`, `AuthorityRevision`, `ObservedAt`, and `ValidUntil`. `GovernanceSigningRecovery` uses the same fields with `NoIssueReceiptId` in place of `ProofId`. Original and recovery bases may differ after a fresh read but must retain the same immutable terminal no-issue identity. Historical DateTimeOffset observations preserve native 100 ns ordering and exclusive observation limits; their comparison does not assert that an old lease is live now and adds no expiry to the capability.

Every original JWS is verified directly against retained capability trust. An unissued attempt needs no invented issue or dispatch request. Signing ids, anchor references and detached digests must match the complete native originals. Receipt and operation identities cannot denote conflicting records across the guard and no-issue inventories. A committed guard original for an obsolete/unissued attempt contradicts its no-issue claim and rejects the observation.

The decoded intent is a closed native `GovernanceGuardTransition` with its complete `GovernanceBatchCommand`, including the original signed capability, JWS, signing id, full ordered target vector and manifest. The verifier checks exact native System.Text.Json bytes, uppercase SHA-256 equality with the receipt's `IntentDigest`, deterministic issue operation identity, tenant/deletion/batch/signing bindings and expected guard comparison. Joint target mutations must be empty; unrelated hold, write, repair, bridge and revocation inputs are refused. The native operation must be the matching issuance, replacement or explicit stale-issuance operation. Missing, duplicate, changed or non-native intent bytes fail closed. The final Signed original must equal the actual consumed request already bound to its retained issue, dispatch, owner and provider originals.

The cross-language test compiles the actual C# signer outcome/proof/successor and guard contract types, roundtrips these native records and intent bytes, and compares successor construction. Its disposable keys and source fixtures supply component evidence only. Installed role programs must capture the actual complete original chain before effects and observe it independently. These offline consistency checks do not prove the completeness/currentness of an installed append inventory, an independent issuer, linearizable reads, physical provenance or all-copy erasure.

## Recovery

Every destructive invocation has a complete original `.request.json` durably fsynced before dispatch, followed by a separate immutable result file. An uncertain result, timeout or invalid proof triggers only `LookupOriginalOperation` with the original operation id, original request digest and original request. A changed identity, pending, unknown or unavailable outcome stops the run. No replacement batch or authorization is minted. Reserved recovery remains the protection owner's same original operation. Seal identities retain the original request digest without retaining canary plaintext.

Before executor mutation, `RegisterOriginalOperation` independently retains the original operation id and complete request digest under the enrolled attempt. Its acknowledgement loss also uses exact lookup. `LookupAttemptOperations` must later supply the signed complete inventory; local recovery refuses a missing, empty, changed or incomplete original journal.

For recovery-only execution, add `--recover-journal` naming the retained original `original-operations` directory. A fresh recovery directory links the original binding and records exact lookups; it never reruns the case plan or enrolls a successor attempt. Original journals remain intact. The standalone recovery of a seal identity does not authorize re-encryption. Successful recovery reports `RECOVERED` with `qualificationPassed:false`; it cannot qualify a plan that did not finish.

## Limits that prevent acceptance today

Platform's [October 29 source handback](../../../platform/docs/implementation/ext-protection-1-erc-component-delivery-2026-10-29.md) supplies custody, private authority/receiving/composition and three qualification-role programs, with source mappings for all 41 cases. Older statements that these source implementations are absent are superseded. The complete installed 41-case role run has not occurred. The independent deployments, accepted profile, exact grants, public anchors and complete immutable coordinated targets remain unqualified or absent. The existing operational OpenBao reference is HMAC only; the separate disposable ERC native evidence uses synthetic private eligibility and does not qualify historical storage, memory, backup or operator copies.

The harness verifies the full deletion-capability JWS against separate accepted public trust and reconstructs native issue/dispatch and consumed owner/provider/terminal-original correlation offline. Hold-order, pin, coverage, re-attestation, replacement-blocked activation, and restore checks also reject a substituted native original. These checks do not establish installed online currentness, sole unrevoked authority, linearizable reads, authenticated physical provenance, all-copy destruction or nonrollback restore. Complete copy-policy authority must remain absent or denying until independently qualified; successful trim or refusal of old ciphertext alone is insufficient. The unchanged 41-case plan and its source mapping do not establish the complete installed pass path. G1–G7 retain their outstanding qualification and acceptance requirements; no cohort or Live execution is authorized by this source delivery, and no complete `Committed` proposal is made.
