# Dapr Infrastructure Boundary

Use this guide when adding or changing an EventStore infrastructure operation. It records the project-wide policy, a preliminary classification of known paths, and the evidence required before selecting a backend or accepting an exception. The final evaluated inventory and automated guard belong to backlog Story 3.17.

> **Prerequisites:** [Architecture Overview](architecture-overview.md), [DAPR Component Reference](../guides/dapr-component-reference.md)

## Required Boundary

EventStore application and shared runtime code must use suitable Dapr building blocks and components for persistence and actors, messaging, service invocation, configuration, secrets, bindings, scheduling/workflows, and cryptographic provider operations where applicable. This covers production libraries, hosts, samples, linked source, and generated-host inputs. Domain modules continue to consume platform seams and receive no direct persistence authority.

For an operation supported by a suitable Dapr interface, application code must not add a database driver, broker client, cloud SDK, provider HTTP call, provider connection string, or provider schema dependency. A missing SDK helper does not justify bypassing a supported Dapr API. A generic binding carrying application-owned SQL or provider protocols does not establish backend portability or override actor ownership.

Suitability means that the operation meets its required correctness, security, compatibility, and operational guarantees on an identified runtime/client/component profile. Record the guarantees and observed evidence. Convenience, familiarity, or an unmeasured performance preference is not a capability gap. Unknown suitability remains unresolved; a Dapr failure must never trigger silent direct-provider fallback.

Hexalith.Platform selects and configures concrete backends through Dapr components within the approved deployment profile and owns infrastructure lifecycle, provider faults, diagnostics and profile-specific qualification execution. EventStore declares required Dapr capabilities, supplies reusable contract tests and application assertions, and consumes Platform-supplied run-owned endpoints and exact loaded identities. Acceptance writes and reads traverse supported Dapr APIs and owning actor boundaries. A profile change still requires compatibility tests and separately authorized data migration where necessary. Qualify ETags, transaction scope, TTL, ordering, cancellation, retries, failure classification, identity, and isolation as applicable to the operation. Missing guarantees remain unresolved; sharing a physical backend does not create transactions across actors, state components, pub/sub, or external systems. Existing repository infrastructure fixtures are retained until an approved Platform replacement is validated and do not authorize new module-owned infrastructure or provider clients.

The planning authority is [PRD §8.4](../../_bmad-output/planning-artifacts/prd.md#84-dapr-infrastructure-boundary) and architecture AD-1/AD-3/AD-23/AD-26. This policy does not establish production readiness or replace the existing readiness, release, security, and consumer-authority gates.

## Open Module Boundary Follow-ups

The 2026-11-09 ownership audit found three unresolved paths: Testing.Integration's Redis/physical-actor-key stream reader, the Platform integration test's direct Redis persistence probe, and Admin's generic-state/private actor-key fallback. Stories 7.11/5.6 own the Dapr-path repairs, 3.18 owns public/behavioral compatibility, 7.19 preserves honest Admin evidence states, and 3.17 inventories/enforces the result. The approved SignalR and Azure decisions do not cover these paths. Until actual implementation and live/package validation pass, they remain known gaps rather than accepted diagnostics or conformant helpers.

Platform owns concrete environment lifecycle, provider/component configuration and profile/fault/restore execution. EventStore contributes backend-neutral Dapr assertions and consumes the existing run-owned descriptor and private credential channels. Provider diagnostics cannot replace logical owning-actor acceptance. The unsupported mandatory append primitive remains independently blocked; changing ownership or repairing readback cannot supply it.

## Notification And Crypto Qualification

Story 2.13 compared Dapr pub/sub fan-out to locally connected hubs and the Azure SignalR output binding with the self-hosted Redis backplane. Local runs with two hosts and independent sidecars delivered the signal and the scoped detail to both hosts with matching persisted readback. Tenant denials, the metadata ceilings (16 entries, 2,048 serialized UTF-8 bytes), connection-reset and silent-discard outages, and fresh-endpoint replica restart also passed. Three gaps blocked a Dapr replacement:

1. **Tenant enrollment.** `pubsub.redis` treats the shipped wildcard subscription `*.*.projection-changed` as one literal stream, so concrete tenant topics are not delivered. Fan-out worked only with exact per-tenant subscriptions and an operator sidecar reload.
2. **Replica restart.** With stock daprd 1.18.x, the surviving host's remote actor call fails after a peer restarts on the same internal endpoint. Only a disposable patched runtime passed.
3. **Production profile.** The self-hosted Kubernetes target runs Dapr 1.18.1, below the AD-26 floor, with no durable broker or binding-capable issuer selected. Azure is outside MVP.

On 2026-10-25 the owner accepted a scoped exception for the retained backplane instead. Its paths, configuration keys, alternatives and removal trigger are in the [register](../architecture/dapr-infrastructure-exceptions.yaml). Results, commands and run identities are in the [Story 2.13 story](../../_bmad-output/implementation-artifacts/2-13-dapr-notification-distribution-qualification.md) per architecture AD-12. Earlier qualification write-ups remain in Git history. Story 3.17 inventories the exception paths and enforces them in its guard.

Story 8.6 must qualify the exact Dapr runtime/client/crypto component for current-version discovery, exact-version wrap/unwrap, RSA-HSM-3072 and RSA-OAEP-256 validation, deterministic identity and least privilege, private connectivity, cancellation, combined retry budgets, typed failures, key custody, buffer ownership/zeroing, historical decryptability, and rollback. Component existence or an encrypt/decrypt happy path is insufficient. Dapr Crypto Scheme v1 must not replace frozen `pdenc-v2`/AAD bytes. The October detached Dapr amendment remains draft/unapproved. The separately approved November SDK exception below preserves the shared engine authority and approval packets.

## Exception Decisions

The [accepted-exception register](../architecture/dapr-infrastructure-exceptions.yaml) holds the Story 2.13 SignalR Redis backplane and the scoped Story 8.6 Azure key-operation exception. Administrator approved the latter on 2026-11-03, including its Core 1.64.0 correction, under single-maintainer attestation. Its exact normative digests are `fcf861aa3ba5d723ca589a8ac8a2a31c54a972fe96a28ec71db69e560ecc2394` and `360da00f91d3134054e4ec3f18c0b96921a36911a89d5935e7d59409634ca07e`.

The investigated Dapr 1.18.7 executable returns 501 for bare metadata/wrap/unwrap; the tagged implementation also lacks required profile and failure guarantees. The approved isolated companion may use `KeyClient.GetKeyAsync` and versioned remote wrap/unwrap POSTs through Azure.Core, all with API `2025-07-01`. Only ordinary Premium RSA-HSM-3072, RSA-OAEP-256, exact historical versions and deterministic managed identity are covered. No SDK dependency enters Contracts, the engine or Server. See the [source-bound qualification](../../_bmad-output/implementation-artifacts/story-8-6-dapr-qualification.md) and [approved design](../../_bmad-output/implementation-artifacts/spec-8-6-crypto-boundary-amendment.md).

The exception does not establish Azure custody or live conformance. Lost wrap outcomes can remain pending indefinitely; provider 404 cannot prove lifecycle deletion or operation absence. Azure provisioning, resource/identity/network/fault mutations, Server activation, release and G5 retain their separate authority. Re-review changes to any runtime, component, SDK, API, credential, profile, path or operation; remove only after an identified released Dapr profile passes the same real-service suite under an approved migration. Missing qualification is not evidence of a permanent capability gap.

The interactive user approved the exact [diagnostic supplement](../../_bmad-output/implementation-artifacts/spec-8-6-identity-diagnostics-disposition.md), normative SHA-256 `a0a746aeab4de17c1b1b95cfa37fbf42a119e29af0c7354fe174d09512b389d9`: only the selected client identifier may appear in Azure-Identity LogMsalAlways24 and ManagedIdentityCredentialSelected26. Public diagnostic flags remain disabled; complete payload scans and all other channel/value prohibitions remain. [The content-bound owner record](../../_bmad-output/implementation-artifacts/story-8-6-identity-diagnostics-owner-approval.json) claims no independent review, Azure conformance or live-run authority. Separately supplied live authority must bind this digest.

Before introducing an operation-specific bypass, retain:

1. The operation, required guarantee, exact Dapr runtime/client/component profile, reproducible gap evidence, and alternatives considered.
2. The isolated adapter, exact allowed source/project/configuration paths, runtime credential boundary, owner, and review/removal trigger.
3. The architecture-owner decision and evidence reference, plus Security/Operations/compatibility decisions where applicable.
4. Guard validation proving the exception cannot authorize unrelated dependencies, linked/generated assets, raw HTTP, or credentials.

Unknown, missing, invalid, stale, or overbroad decisions stay unresolved and cannot supply conformance. Story 3.17 owns the final machine-checked schema and guard implementation after graph inspection. Static analysis must state its limits; dependency names or source scans cannot prove complete network enforcement.
