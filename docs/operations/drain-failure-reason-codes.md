# Drain Failure Reason Codes

Aggregate drain failures are reported through the `eventstore.failure_reason` activity tag and matching structured-log context. These values are a stable observability contract: add new values only when a deterministic operation boundary exists, never by parsing localized exception text, and never rename or repurpose an existing value without a compatibility plan.

| Reason code | Emitted when | Retry expectation | Operator action | Compatibility rule |
| --- | --- | --- | --- | --- |
| `drain_event_count_mismatch` | The drain record event count does not match its persisted sequence range. | Automatic retry is not expected to repair the record. | Inspect the drain record and event stream for corruption before manual recovery. | Stable DW1 value; do not rename. |
| `drain_missing_event` | A persisted sequence in the drain range is missing. | Automatic retry is not expected to recreate the missing event. | Inspect state-store contents for the aggregate stream and repair through an explicit recovery path. | Stable DW1 value; do not rename. |
| `drain_publish_failed` | The drain publish operation returns an unsuccessful result, or throws at the publish boundary with a known infrastructure exception type (`DaprException`, `RpcException`, `HttpRequestException`, `IOException`, `TimeoutException`). Programmer-error exceptions (e.g. `NullReferenceException`, `ArgumentException`) propagate raw and classify as `unknown` so real defects surface. | Retryable while pub/sub or subscriber infrastructure recovers. | Check pub/sub component health and publisher logs; raw publisher details stay in structured logs, not the activity tag. | Stable DW1 value; do not rename. |
| `drain_state_store_failure` | The drain operation fails at a controlled actor state-store boundary while loading or saving drain state/events; payload deserialization (`EventDeserializationException`) at that boundary; or a plain `DaprException` without an inner availability signal (e.g. permanent state-store/component config error). | Usually retryable if the state store or DAPR sidecar recovers; not retryable for payload schema corruption or component misconfiguration. | Check state-store availability, DAPR sidecar/component config, ETag/conflict symptoms, storage health, and event payload schema. | Additive DW8 value; future state-store subcategories (e.g. concurrency, payload-invalid) require tests and a doc update. |
| `drain_dapr_unavailable` | An explicit DAPR/runtime availability signal is observed: gRPC `Unavailable`, `DeadlineExceeded`, `ResourceExhausted`, or HTTP `503`, `502`, `504`, `408`, `429` (request timeouts, gateway errors, throttling). `Aborted` (concurrency/transactional abort) is NOT in this set; it falls through to a state-store/concurrency code or `unknown`. | Retryable while DAPR placement, sidecar, runtime, or downstream infrastructure recovers. | Check DAPR sidecar/runtime health, actor placement availability, and downstream throttling/back-pressure. | Additive DW8 value; keep narrow to availability/throttling signals. |
| `drain_attempts_exhausted` | The persisted drain `RetryCount` has reached `EventStore:Drain:MaxDrainAttempts` (default `8`). Checked *before* each publish attempt, so the bound is a real bound. | Not retryable. No further automatic attempt is made; the committed range is published to the tenant dead-letter topic instead. | Consume the dead-letter message: it carries the correlation ID, command type, and the persisted `StartSequence`/`EndSequence` of the range that was never published. It is a **reduced** envelope — `ReplayEligible` is `false` and the original command payload is absent, so it must not be fed back through replay. Investigate why publication never succeeded before republishing the range by an explicit operator path. | Additive Story 4.4 value; do not rename. |
| `unknown` | The failure is uncategorized or lacks a deterministic operation boundary. | Depends on the underlying exception. | Inspect structured logs for the exception type/message and open a classifier follow-up if the same failure repeats. | Stable residual value; do not replace with `drain_failure_unknown`. |

The observable surfaces are activity tags, structured logs, focused server tests, and any dashboard or trace view that reads the activity tag. Raw exception text can appear in logs for diagnostics, but activity tags must stay bounded to the reason codes above.

Drain records are not DAPR subscriber dead letters. A drain record means EventStore has persisted events that still need a confirmed DAPR publish acceptance or an explicit manual repair path. DAPR subscriber dead-letter topics mean a subscriber failed after delivery retry exhaustion. For `drain_event_count_mismatch` and `drain_missing_event`, preserve the drain record and inspect the sequence range, command type, correlation ID, retry count, and last failure reason; do not copy event payload bytes, protected data, connection strings, or subscriber credentials into repair notes or operator-visible diagnostics.

`drain_attempts_exhausted` is the one exception to "inspect the drain record". Exhaustion **removes** the drain record, its recovery index entry and its reminder once the dead-letter publish is accepted, so there is nothing left in actor state to inspect afterwards — the dead-letter message is the record of what happened. The removal only runs after the sink accepts: if the dead-letter publish fails, the drain record, the index entry and the reminder are all retained and the range is retried later, so committed events are never dropped because the sink was unavailable. Exhaustion also releases the command's `Recoverable` idempotency disposition to `Terminal`, so normal retention resumes and a later retry of the same message ID no longer returns a recoverable outcome.

## Command status retryability

The command-status poll endpoint carries the same disposition additively, alongside these reason codes:

| Field | Meaning |
| --- | --- |
| `retryable` | `true` — a drain is armed and will retry automatically. `false` — terminal, no further automatic attempt (attempts exhausted, dead-lettered, or no reminder armed). `null` — a record written before this field existed; **never** read `null` as "permanently failed". |
| `recoveryReasonCode` | The reason code from the table above that explains the current disposition. |
| `drainAttemptCount` | Drain attempts made so far for this range. |
