# Command recovery integrity — DW-499 / DW-502

Recorded before implementation on 2026-10-14 against EventStore `173ad7f4e56a72f44621c7d3d7be86a5ec19dc03`. This bounded repair follows architecture AD-1/AD-5/AD-8/AD-12, the command lifecycle, and the existing advisory-status and exact-checkpoint contracts. It does not qualify production delivery or change opaque-key admission replay.

## Terminal advisory repair

Advisory status remains non-authoritative and ordinary status-store failures cannot change a committed logical outcome. Before deleting the pipeline or successful drain, the actor stages an immutable terminal advisory intent and a fixed-key discoverability index in the same actor-state transaction as terminal idempotency, cleanup and publication-owner accounting. The intent binds actor tenant/domain/aggregate, original MessageId, correlation, normalized causation, command type, count, original start/end range, and the exact terminal status record. Completed sequence proof is retained only when the original committed range was verified; rejection and no-op retain null proof. Never read the aggregate head to recreate command proof.

After the terminal batch is durably confirmed, a best-effort writer publishes the persisted status record. Only confirmed write success permits removing the pending intent and its index entry. A failed or ambiguous acknowledgement cleanup leaves retryable durable evidence; state-cache discard/inspection follows existing remediation seams. Repeated writes of the same terminal record are safe. A crash before terminal commit preserves the existing checkpoint; a crash after commit leaves the discoverable intent. Activation performs bounded reminder rearming, never publication or domain execution. A reminder retries pending advisory writes independently of event-drain ownership. Exact aggregate terminal duplicates may repair only the matching persisted intent and must return the unchanged cached result; identity conflicts and opaque admission equivalent replay never use this repair seam. Already repaired duplicates do no advisory write. Legacy terminal records without an intent stay cached with no invented proof.

## Unverifiable publication refusal and recovery

The platform extends the existing `command_identity_conflict` refusal rather than adding a public quarantine status. Resume requires actor partition equals command tenant/domain/aggregate, complete exact checkpoint MessageId/correlation/command type/normalized causation, a defined nonnegative count, and a coherent original range. Eventful ranges require positive contiguous start/end, exact count, every expected envelope present, and every envelope's tenant/domain/aggregate/sequence/correlation/causation matching. No-op checkpoints require zero count and no event range. Verification precedes every publisher call and every transition that could release retained evidence. Missing/legacy identity or range evidence is unverifiable, never inferred from stream head, current command, or unrelated events.

Unverifiable direct resume returns `Accepted=false`, `ErrorMessage=command_identity_conflict`, and the incoming correlation, with zero domain invocation, persistence, publication or cleanup of the checkpoint/envelopes. Missing/corrupt/invalid range preparation retains evidence rather than converting it to a normal publication failure. A transient state-read failure also publishes nothing and preserves recovery evidence; cancellation propagates. Stale-checkpoint handoff and activation/reminder recovery must not bypass verification. Invalid drain evidence stays retained without consuming the normal publication retry budget or triggering exhaustion cleanup/dead-lettering. Valid persisted ranges retain existing resume/drain success and publication-failure semantics, including legacy drain records only when existing persisted idempotency evidence proves the same exact causation.

The owning recovery path is inspection through existing actor/operator seams, immutable backup preservation, and a separately authorized restore/reconciliation of exact command evidence from a trusted backup. Retry the same command or existing reminder only after that evidence is restored; every retry revalidates it. Automatic rewriting, guessing, skipping events, production replay or migration is not authorized. There is no new claim that legacy evidence can always be recovered, nor a new operator endpoint or CLI. Other commands/aggregates and their evidence remain untouched.

## Verification boundary

Fault-injection tests inspect durable actor-state end-state across failed writes, before/after-commit failures, actor recreation and repeated recovery. They prove original proof ranges, exact duplicate behavior, refusal with zero pub/sub, verified restore/resume and unrelated-owner preservation. In-memory persistence/fault tests do not supply production-provider, multi-host, sealed CI or rollout qualification.
