# Isolated Azure qualification

This project is explicitly invoked. Its default execution fails before any Azure call or fixture setup unless separate, unexpired, exact-content environment authority is supplied. A local build or an unexecuted suite supplies no Azure conformance.

Use the manual `Payload Protection Azure` workflow on the protected `payload-protection-azure-conformance` environment and the `payload-protection-azure-private-ephemeral` runner group. Operators must supply an ephemeral Linux x64 managed-identity runner inside the approved VNet, Docker, and the exact Dapr 1.18.7 executable SHA-256 `e988a6f53abec017fc9ebcb4f89de9bed11bce005eb49bd8e85e8d3d6adbf488`. The workflow verifies that binary and uses the same pinned isolated PostgreSQL image as PF-02. It does not install or mutate Azure infrastructure.

Supply `PAYLOAD_AZURE_AUTHORITY_JSON` and `PAYLOAD_AZURE_CUSTODY_JSON` as protected environment secrets. The manual `authority_sha256` input is SHA-256 over the exact UTF-8 authority secret bytes. The test loader also verifies the custody receipt's exact SHA-256, source revision, expiry and required fields. Provisioning/identity/network/fault preparation needs its own owner authority; these documents record that external scope without granting it.

The authority JSON uses the exact property names of `AzureLiveAuthority`: named `Owner`, canonical checkout `SourceSha`, UTC `ExpiresAtUtc` within one day, resource/identity/network hashes, `Region`, `VaultUri`, `KeyName`, canonical runtime and denied-identity client IDs, and exact full `InitialVersion`, `RotationVersion`, `DisabledVersion`, `ExpiredVersion` and `MissingVersion` IDs for that one vault/key. Each version must be distinct. Include the approved exception/correction digests, `DiagnosticPolicyDigest` exactly `a0a746aeab4de17c1b1b95cfa37fbf42a119e29af0c7354fe174d09512b389d9`, and `CustodyReceiptSha256`. Unknown or duplicate JSON properties fail closed.

That diagnostic policy permits only the configured selected managed-identity client identifier in the pinned vendor's Azure-Identity LogMsalAlways (event 24) and ManagedIdentityCredentialSelected (event 26) payloads. Other channels and protected values remain prohibited. Public diagnostic switches remain disabled; live observers apply the same narrow classifier as the unit lane and export only safe categories, counts and fingerprints.

`Operations` is exactly `get-key`, `wrapkey`, `unwrapkey`, `isolated-dapr-persistence`, `engine-rewrap`, `read-only-rollback`, `cleanup-isolated-dapr`, `retain-all-azure-keys`. `Faults` is exactly `401`, `403`, `404`, `disabled`, `expired`, `429`, `timeout`, `dns`, `5xx`, `cancellation`, `breaker`, `lost-wrap-response`.

`FaultWindows` contains four externally prepared intervals, one each for `429`, `5xx`, `timeout`, and `dns`, with `Fault`, `NotBeforeUtc`, and `NotAfterUtc` fields. Each lasts at most three minutes and ends before authority expiry. Schedule them after fixture readiness, in non-overlapping UTC order, with at least 35 seconds between intervals for circuit recovery. The operator's separately authorized controller must limit 429/5xx/stall faults to wrap POSTs, preserving metadata access; DNS failure is pre-dispatch. The suite waits for each interval, makes real requests, requires actual observed crypto 429/5xx status or the specified pre/post-dispatch evidence, then verifies recovery and retained Dapr state. It never fabricates these observations. Missed windows or unexpected outcomes fail the gate.

The custody receipt uses the exact constructor fields of `AzureCustodyReceipt`. It records the ordinary Premium resource, provider-generated non-exportable RSA-HSM-3072 key, 90-day retention and purge protection, private endpoint/DNS, disabled public access and trusted-service bypass, the key-scoped runtime role, separate provisioning identity and diagnostic-sink hash. This is operator-supplied custody evidence; metadata alone cannot establish those controls.

For a separately authorized local run, set `HEXALITH_PAYLOAD_AZURE_LIVE=authorized`, `HEXALITH_PAYLOAD_AZURE_AUTHORITY`, `HEXALITH_PAYLOAD_AZURE_AUTHORITY_SHA256`, `HEXALITH_PAYLOAD_AZURE_CUSTODY_RECEIPT`, and `HEXALITH_PAYLOAD_AZURE_SOURCE_SHA`, then invoke the built assembly. Do not copy the private receipt or raw provider IDs into logs or artifacts.

The history test persists event/snapshot bytes through the fixture's owning Dapr state boundary, verifies wrapped-key/index end state, restarts engine instances, rewraps between already provisioned retained versions, and performs the approved ReadOnly rollback for a domain without an approved legacy writer. It does not provision/rotate/delete KEKs or claim Server/Parties integration. The engine boundary-fault theory is labeled separately from real service fault observations. Cleanup removes only the isolated Dapr process, container and temporary files; all Azure versions remain retained. No online invalidation result proves destruction of every backup or recoverable copy. Source SHA, commands, counts, CI URL and limitations belong in the owning story; workflow test output is the retained artifact.

The workflow runs the healthy class first, then the externally prepared fault class in a separate process. Both classes share a non-parallel collection. Each requires its exact `HEXALITH_PAYLOAD_AZURE_PHASE` (`healthy` or `prepared-faults`) before provider calls. Healthy cases require at least five minutes before the first prepared window. Schedule the first window with enough margin for the healthy lane (for example twenty minutes after the authorized job starts); all windows and recovery must fit the forty-minute fault-test and forty-five-minute job budgets. A full-assembly invocation is not the ordered operational entry point: use the same two class filters and phases as the workflow.

Companion registration is passive: it registers options, the backend and an explicit readiness probe, and starts no hosted service or Azure request. Story 8.7 must invoke the fail-closed probe together with PF-02/lifecycle/fence checks only for an explicitly Enabled engine. The current companion cannot enable Server protection by itself. The local sentinel lane covers SDK and HTTP diagnostic sources, activities, metrics, logs and first-chance exceptions. It does not attest raw OS/network EventSources, dump/swap policy, or every observer an arbitrary host might install; those remain deployment/conformance obligations.
