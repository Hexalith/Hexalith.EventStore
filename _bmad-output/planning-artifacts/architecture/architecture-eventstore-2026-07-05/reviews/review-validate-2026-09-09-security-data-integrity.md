# VALIDATE Gate Review - Security / Data-Integrity Lens (2026-09-09)

Spine: `_bmad-output/planning-artifacts/architecture.md` (609 lines, status `final`, updated 2026-08-29).  
Reviewer lens: fail-closed multi-tenant event sourcing, durable mutation ownership, credential and key custody, projection/checkpoint integrity, erasure boundaries, and deployment-provider conformance.

## Verdict

**CHANGES REQUIRED.** The spine contains strong local rules, but it is not yet a safe canonical boundary for independently implemented units. Two critical ambiguities remain: production is allowed to select an actor-state provider despite the absence of append write-once proof, and tenant identity has neither a canonical source nor a normalization rule shared by authorization and storage. Seven high findings leave an application-channel credential undefined, make default-deny optional, fail to bind audit identity atomically to mutations, leave AD-24/AD-25 key-rotation clocks incompatible, permit an unfenced actor mutation path contrary to AD-5, specify normalized projection result types that do not exist, and define `ProjectionVersion` without an authoritative producer rule.

Counts: **critical 2, high 7, medium 4, low 2**.

The deterministic architecture lint was reported as passing with **0 findings**. This review is semantic and critique-only; it did not modify the spine or implementation.

## Method and evidence boundary

1. Read the complete architecture spine, its architecture memlog, the current canonical PRD, the 2026-09-08 authentication-ratification proposal, the current sprint-change proposal, the OpenBao/OQ8 proposals, and the Story 4.5 durability evidence.
2. Inspected the current gateway, domain-service SDK, Operations host, Admin Server, tenant/claims code, actor mutation path, idempotency admission/key provider, projection dispatcher/rebuild/checkpoint path, read-model erasure path, DAPR components, and production state-store templates.
3. Treated the spine as a coordination contract: a finding exists when two separately built units can take different security or integrity decisions while each plausibly claims conformance, or when the adopted text is contradicted by the current brownfield path it purports to ratify.
4. No build or test was run because this is a document-validation review. Repository-wide exact-symbol searches are used only for absence findings and are paired with concrete current contract/call-site evidence.

Severity means: **critical** permits tenant breach, silent event loss, or unsupported production durability while conforming to the text; **high** permits a plausible fail-open, forged attribution, duplicate effect, or checkpoint/provenance divergence; **medium/low** are hardening or explicitly identified code/document drift.

## Critical findings

### C1 - Production actor-state provider is not selected, while one supported-looking profile is proven lossy and another is unproven

- **Spine evidence:** AD-5 explicitly says physical write-once enforcement is unavailable (`architecture.md:117-121`). AD-25 names PostgreSQL only as the *approved production-equivalent evidence profile* (`architecture.md:451-460`), not as the production provider. The Stack has no actor-state-provider row (`architecture.md:486-513`). Runtime topology requires profiles to remain aligned but does not constrain provider choice (`architecture.md:483`). Deferred repeats that Redis can silently overwrite a durable sequence-1 write and that no behavior is inferred for another provider (`architecture.md:598-609`, especially `:606`).
- **Repository evidence:** local AppHost uses `state.redis` with `actorStateStore: true` (`src/Hexalith.EventStore.AppHost/DaprComponents/statestore.yaml:21-40`). Production templates present both PostgreSQL (`deploy/dapr/statestore-postgresql.yaml:15-29`) and Cosmos DB (`deploy/dapr/statestore-cosmosdb.yaml:15-36`) as the same `statestore` actor component. Story 4.5 observed the raw durable contender disappear and the actor accept without a conflict (`_bmad-output/implementation-artifacts/4-5-append-durability-race-evidence.md:13-18`), and states that the observed Redis profile permits silent same-sequence loss (`:61-63`).
- **Exploit/divergence scenario:** deployment unit A chooses PostgreSQL because AD-25 used it for OQ8; deployment unit B chooses the shipped Cosmos profile because it is labelled Production; a developer-derived deployment carries the AppHost Redis component. All can cite AD-9 and the absence of a Stack constraint. A duplicate activation or unsupported writer can then overwrite an already durable event on the proven Redis profile, while Cosmos has no equivalent evidence at all. Admission fencing does not make the storage write first-write-only.
- **Impact:** silent event replacement/loss, false gapless history, downstream projections derived from a different history, and a production profile claiming durability it has not proved.
- **Disposition:** **discuss, then autofix**. Owner must select the production actor provider or explicitly declare that no production deployment is conforming yet. Add a Stack/convention row naming `state.postgresql` / `oq8-postgresql-v1` as the sole currently proved production actor profile; constrain Redis to Development; mark Cosmos non-authorizing until it passes the same persisted append-race and AD-25 evidence. Retain the honest statement that this mitigates but does not provide provider-portable write-once enforcement.

### C2 - Tenant identity has no canonical source or normalization boundary; authorization and state identity already disagree

- **Spine evidence:** AD-10 requires “tenant authorization” without defining the operating tenant (`architecture.md:147-151`). The State keys convention says only that tenant stays explicit across keys, topics, query scopes, SignalR groups, and admin filters (`architecture.md:462-470`); it does not say where tenant originates, its canonical form, or whether omission is legal. AD-25 says canonical validation precedes admission but does not define tenant canonicalization (`architecture.md:400-415`). PRD NFR2 enumerates isolation surfaces but likewise omits a source/normal form (`prd.md:305-307`).
- **Repository evidence:** durable aggregate identity lowercases tenant/domain before validating them (`src/Hexalith.EventStore.Contracts/Identity/AggregateIdentity.cs:10-38`). JWT transformation copies `tenants`, `tenant_id`, and `tid` values without lowercasing or validating (`src/Hexalith.EventStore/Authentication/EventStoreClaimsTransformation.cs:68-76,79-113`). `ClaimsTenantValidator` compares raw claim and request values with `StringComparison.Ordinal` and even allows a global administrator to pass an empty tenant (`src/Hexalith.EventStore/Authorization/ClaimsTenantValidator.cs:22-49`). Admin authorization supplies the first authorized tenant when an explicit action tenant is absent (`src/Hexalith.EventStore.Admin.Server/Authorization/AdminTenantAuthorizationFilter.cs:23-40`), while aggregate identity later canonicalizes it.
- **Exploit/divergence scenario:** a principal has grant `Tenant-A`; gateway authorization rejects request tenant `tenant-a` while a global-admin or admin fallback path accepts it, and the storage identity silently rewrites it to `tenant-a`. Conversely, an omitted tenant is defaulted by Admin Server but rejected by gateway. Admission keys, audit records, SignalR groups, and state keys can consequently refer to different strings for the same operation, or an admin action can target whichever grant happens to be first.
- **Impact:** authorization/storage split, incorrect tenant audit attribution, unreachable or aliased idempotency records, cross-surface tenant confusion, and potential cross-tenant disclosure through defaulted admin queries.
- **Disposition:** **autofix**. Add one binding tenant-identity convention: the explicit request/envelope tenant is mandatory at the first application boundary; omission is rejected, never defaulted; a single platform canonicalizer validates and normalizes it before authorization and before any key/actor/topic/group derivation; grants are normalized with the same function; downstream services carry the validated canonical tenant and never re-derive it. Define global-admin handling and reserve `system` consistently.

## High findings

### H1 - AD-10 does not name the inbound sidecar-to-application credential; three incompatible implementations exist

- **Spine evidence:** all internal/domain/projection/admin-computation endpoints require application-layer credentials and must not trust DAPR ACLs or network location (`architecture.md:147-151`). AD-18 defines only *outbound* ownership of `dapr-app-id` and `dapr-api-token` (`architecture.md:269-284`). No decision defines what a receiver validates.
- **Repository evidence:** gateway internal authentication accepts an allow-listed `dapr-caller-app-id` header and creates a `global_admin` principal (`src/Hexalith.EventStore/Extensions/ServiceCollectionExtensions.cs:65-101`; `src/Hexalith.EventStore/Authentication/DaprInternalAuthenticationHandler.cs:20-45`). Operations instead validates `dapr-api-token` against `APP_API_TOKEN` in fixed time (`src/Hexalith.EventStore.Operations/Security/DaprAppChannelTokenMiddleware.cs:11-44`) and requires it outside Development (`DaprAppChannelSecurity.cs:11-22`). The domain-service SDK maps `/process`, `/replay-state`, `/query`, `/project*`, rebuild, and catalog endpoints without authentication or authorization (`src/Hexalith.EventStore.DomainService/EventStoreDomainServiceExtensions.cs:121-174,198-330`), and its service registration adds DAPR/DataProtection/domain services but no authentication (`:404-463`).
- **Exploit/divergence scenario:** a workload reaches a domain service’s application port directly and submits a forged tenant envelope; or it sends an allow-listed `dapr-caller-app-id` directly to the gateway and receives system-wide administrator identity if network controls do not guarantee sidecar provenance. Meanwhile Operations requires a real secret. Each unit can claim some part of AD-10, but their trust models are incompatible.
- **Disposition:** **autofix**. Define the DAPR application-channel token as the receiver-validated credential for every non-probe sidecar-to-app hop, make the middleware platform-owned and installed by the domain-service SDK/gateway/Operations, and state that `dapr-caller-app-id` plus ACL is attribution/defense-in-depth only. Require startup/readiness failure outside Development if the token is absent. If a different credential is intended, name it and its issuer, receiver validation, rotation, and forwarding rules just as precisely.

### H2 - Deny-by-default is optional in the spine and absent in current hosts

- **Spine evidence:** AD-16 says “any host that introduces a global fallback authorization policy” must coordinate probe exemptions (`architecture.md:243-253`), making the policy conditional even though AD-10/NFR1 say fail closed. The convention calls probes the only anonymous exception (`architecture.md:473`) without requiring a mechanism that makes accidental endpoint omission fail closed.
- **Repository evidence:** gateway registration ends with `AddAuthorization()` and no `FallbackPolicy` (`src/Hexalith.EventStore/Extensions/ServiceCollectionExtensions.cs:97-103`). Domain-service endpoints have neither per-route authorization nor a fallback (H1). A repository search found no `FallbackPolicy` assignment under `src/`.
- **Exploit/divergence scenario:** a new controller or minimal API endpoint omits `[Authorize]` / `RequireAuthorization`; it is anonymous despite satisfying normal compilation and topology tests. A representative protected-endpoint denial test does not detect another anonymous map.
- **Disposition:** **autofix**. Require every HTTP host to install a platform fallback policy requiring an authenticated user or the platform app-channel credential. Make anonymous routes an explicit allowlist (`/health`, `/alive`, `/ready`, plus any separately adopted static public route) and add structural endpoint-metadata evidence for every host kind.

### H3 - “Attributable” admin mutation does not define an authenticated identity or atomic audit/mutation unit

- **Spine evidence:** AD-10 only says admin state mutations are “attributable and support-safe” (`architecture.md:147-151`). The earlier architecture decision was stronger—authenticated user, tenant, action, outcome, and correlation (`architecture-eventstore-2026-07-05/.memlog.md:28-29`)—but that contract did not survive into the spine. The Deferred table postpones audit-record deletion without defining the active audit record’s authority or durability (`architecture.md:609`).
- **Repository evidence:** `HttpContextAdminAuthContext` can derive `sub`/name identifier and correlation (`src/Hexalith.EventStore.Admin.Server/Services/HttpContextAdminAuthContext.cs:28-40`), but an admin mutation falls back to `"anonymous"` (`src/Hexalith.EventStore.Admin.Server/Controllers/AdminBackupsController.cs:281-299`) and services also use `"anonymous"` (`src/Hexalith.EventStore.Admin.Server/Services/DaprBackupCommandService.cs:490-494`). Other workflows accept `request.OperatorActorId` and persist it as `DecisionActorId` (`DaprBackupCommandService.cs:334-380`). Admission decisions write an audit row and the changed state in two independent `SaveStateAsync` calls (`:289-329`); workflow creation uses three separate writes (`:350-395`).
- **Exploit/divergence scenario:** a caller supplies another operator’s identifier; or an authenticated mutation is recorded as anonymous. If audit save succeeds and state save fails, support sees an audit of a decision that never took effect. If one of the workflow index writes fails, audit, workflow-id index, and scope state disagree. Retrying cannot distinguish all partial states from a completed decision.
- **Disposition:** **autofix**. Define the audit subject as authenticated `sub` (never caller body/query data and never a placeholder), the required fields (canonical tenant, action, target, requested and final outcome, correlation, surface/delegator, timestamp), append-only semantics, and an atomic same-store transaction or versioned resumable protocol binding audit and mutation. Reject mutations whose subject is unavailable. State how MCP/service delegation preserves the human/operator identity.

### H4 - AD-24 revocation and AD-25 digest-key retirement have incompatible clocks

- **Spine evidence:** AD-24 says rotation completes after consumer acknowledgement and then revokes old material (`architecture.md:390-392`). AD-25 requires active plus all retained-reader aliases to find the one canonical actor and refuses retirement while records, tombstones, aliases, migration entries, or holds reference the version (`architecture.md:428-440`). AD-24’s catalog contract does not explicitly name the admission digest ring or subordinate revocation to AD-25 retirement (`architecture.md:384-390`).
- **Repository evidence:** runtime admission can select a DAPR secret map by arbitrary store/name/generation (`src/Hexalith.EventStore.Server/Configuration/IdempotencyAdmissionOptions.cs:18-31`); validation correctly forbids inline configuration keys outside Development/test, but accepts any named DAPR secret store (`ValidateIdempotencyAdmissionOptions.cs:38-61`). The provider loads the active and retained reader versions from one map and requires the configured generation (`src/Hexalith.EventStore.Server/Commands/DaprSecretIdempotencyDigestKeyProvider.cs:22-70`).
- **Exploit/divergence scenario:** platform rotation sees all runtime consumers acknowledge generation N+1 and revokes N under AD-24; AD-25 still has tombstones or directory aliases addressed by N. A replay cannot derive its old alias and may appear as fresh executable work, defeating the duplicate-effect fence. A deployment can also use a non-OpenBao DAPR store even though AD-24 intends OpenBao.
- **Disposition:** **autofix**. Catalog the AD-25 ring explicitly as a runtime-required `openbao` logical map. State that AD-24 acknowledgement is necessary but not sufficient: old digest material remains readable until AD-25 proves zero references/holds and authorizes retirement; the directory and secret generation flip are one coordinated protocol. Production validation must require store name `openbao`.

### H5 - The adopted AD-5 “current fence only” rule is contradicted by an unfenced public/actor path

- **Spine evidence:** AD-5 says `AggregateActor` accepts **only** an internal current-fence execution context before domain processing, append, recovery, snapshots, or projection activation (`architecture.md:117-121`). AD-25 says exactly the current non-zero fence may cross aggregate/domain/provider/repository/projection/audit/scheduling boundaries (`architecture.md:406-415`).
- **Repository evidence:** the public DTO calls `IdempotencyKey` optional (`src/Hexalith.EventStore.Contracts/Commands/SubmitCommandRequest.cs:16-26`). Admission runs only when the key is non-null (`src/Hexalith.EventStore.Server/Pipeline/SubmitCommandHandler.cs:55-77`), and a null execution context calls the legacy `RouteCommandAsync` (`:250-281`). `CommandRouter` exposes both unfenced and fenced routes (`src/Hexalith.EventStore.Server/Commands/CommandRouter.cs:33-54,62-99`); `IAggregateActor` publicly exposes `ProcessCommandAsync` beside `ProcessFencedCommandAsync` (`src/Hexalith.EventStore.Server/Actors/IAggregateActor.cs:11-25`). The unfenced actor method passes null, and `EnsureExecutionFenceAsync` treats null as success (`src/Hexalith.EventStore.Server/Actors/AggregateActor.cs:346-371,4167-4179`).
- **Exploit/divergence scenario:** a caller omits the optional key or a trusted internal client invokes the legacy actor method; the mutation, status/archive, projection activation, and domain/provider effects execute without admission serialization or a current fence. Retried cross-target operations can duplicate side effects while the implementation still exposes the AD-5-prohibited entry point.
- **Disposition:** **implementation blocker plus spine clarification**. Either make admission/key mandatory for every mutation and remove/deny the unfenced actor method, or explicitly scope AD-5/AD-25 to a named protected-operation set and define which mutations may remain unfenced and why NFR7(e) does not apply. The current absolute architecture wording and current implementation cannot both be authoritative.

### H6 - AD-19’s sole normalized checkpoint result is a phantom contract

- **Spine evidence:** AD-19 freezes `ProjectionDispatchResult(Version, Entries)`, `ProjectionDispatchResultEntry`, and `ProjectionCheckpointAdvanceState`, and forbids any alternative normalized result (`architecture.md:286-309`). The Projection persistence convention depends on that result to make every route’s checkpoint decision explicit (`architecture.md:477`).
- **Repository evidence:** the actual contract is `ProjectionDispatchResponse(Version, Outcomes)` (`src/Hexalith.EventStore.Contracts/Projections/ProjectionDispatchResponse.cs:3-10`) whose `ProjectionDispatchOutcome` contains projection type, status, optional state, and reason—but no domain or checkpoint advance state (`ProjectionDispatchOutcome.cs:6-17`). The server validates and returns ordered `ProjectionDispatchOutcome[]` (`src/Hexalith.EventStore.Server/Projections/NamedProjectionDispatchCoordinator.cs:152-191,1021-1055`). A repository-wide exact-symbol scan found no declarations or uses of `ProjectionDispatchResult`, `ProjectionDispatchResultEntry`, or `ProjectionCheckpointAdvanceState` under `src/` or `tests/`.
- **Exploit/divergence scenario:** projection unit A treats handler `Completed` as checkpoint advanced; unit B waits for a later checkpoint save; unit C reconstructs advance state from logs. A post-handler persistence or checkpoint failure is not representable in the required normalized type because the type does not exist, so a successful handler outcome can be reported as durable completion while the checkpoint stayed behind.
- **Disposition:** **autofix or implementation blocker**. If AD-19 is the intended authority, add the named server result and persisted-path tests before claiming conformance. If the existing outcome/checkpoint protocol is authoritative, revise AD-19 through an approved decision so there is exactly one real shape and one normalization point.

### H7 - `ProjectionVersion` has no canonical construction/evolution rule and no production model owns it

- **Spine evidence:** AD-15 declares `ProjectionVersion` authoritative only when sourced from persisted `IReadModelFreshness` (`architecture.md:227-241`), but does not define whether it identifies handler code, read-model schema, catalog fingerprint, rebuild generation, or event prefix; AD-20 requires rebuild versions to equal canonical replay without defining the equality identity (`architecture.md:311-315`).
- **Repository evidence:** production code only copies `readModel?.ProjectionVersion` into response metadata (`src/Hexalith.EventStore.Client/Projections/ReadModelFreshnessExtensions.cs:62-85`). Repository uses of `IReadModelFreshness` outside that bridge are test-only model types; no production read-model type or platform write path constructs the version. The gateway correctly clears version on non-projection evidence, but cannot make an arbitrary domain string authoritative.
- **Exploit/divergence scenario:** one projection writes assembly version, another writes projection name, and a third writes a static `v1`; all satisfy the interface. UI/cache/rebuild code compares incomparable strings and can label a stale or differently shaped model current.
- **Disposition:** **autofix**. Define a versioned, bounded canonical projection-version value and its producer: at minimum bind domain, projection type, handler/schema version, catalog fingerprint, and rebuild/live lineage as required; specify when it changes, how legacy/missing values become `Unknown`, and how staged rebuild promotion writes it atomically with detail/index/checkpoint state.

## Medium findings

### M1 - Production secret templates contradict AD-24 and can bypass the adopted credential seam

- **Evidence:** AD-24/NFR17 require dependent components to use `secretKeyRef` with `auth.secretStore: openbao` (`architecture.md:380-390`; `prd.md:320-323`). Current PostgreSQL production template reads a plaintext environment placeholder (`deploy/dapr/statestore-postgresql.yaml:19-29`), and Cosmos reads its master key from an environment placeholder while its comment directs users to Azure Key Vault (`deploy/dapr/statestore-cosmosdb.yaml:20-36`). Neither names `openbao`.
- **Scenario:** a deployment follows the shipped Production template, passes a connection string/master key through environment, and bypasses secret scopes, generation, rotation acknowledgement, and OpenBao policy validation.
- **Disposition:** **defer as implementation drift, but make it a deployment gate**. The spine is clear; no production profile should be called conforming until templates and validation implement it.

### M2 - Erasure has multiple authorities and no tiered completion vocabulary

- **Evidence:** AD-7 defines selected read-model plus delivery/rebuild/checkpoint erasure (`architecture.md:129-133`); AD-23 assigns policy and erasure-state seams for payload protection (`architecture.md:370-378`); full event/broker/backup/audit erasure is deferred (`architecture.md:609`). Mutation convention forbids rewriting persisted events (`architecture.md:470`).
- **Scenario:** one unit returns “erasure complete” after read-model cleanup while another interprets completion as crypto-erasure and an operator assumes physical deletion, even though event, broker, backup, and audit copies remain.
- **Disposition:** **autofix**. Name completion tiers (read-model erasure, payload crypto-erasure, physical erasure), require every status/audit/API to name its tier, state retained artifacts per tier, and forbid generic “erased” completion.

### M3 - Telemetry hygiene is local to a few ADs, not a platform-wide invariant

- **Evidence:** AD-25 forbids raw idempotency keys in all telemetry (`architecture.md:406-410`); AD-24 limits secret diagnostics (`:390-394`); cursors/ETags are not logged (`:475`); NFR5 limits only SignalR metadata logging (`prd.md:309`). There is no equivalent rule for command/event/read-model payloads, bearer/app-channel tokens, tenant grants, personal data, or exception bodies.
- **Scenario:** a new domain endpoint or OpenTelemetry enricher records a serialized envelope or authorization header at Information level and is not in conflict with any general spine convention.
- **Disposition:** **autofix**. Add a platform telemetry classification/redaction convention covering logs, traces, metrics, ProblemDetails, admin/CLI/MCP output, and retained evidence; allow bounded identity metadata/outcome codes and prohibit payloads, credentials, key material, raw opaque tokens/cursors/ETags, and personal data outside an explicitly approved Development-only diagnostic.

### M4 - Operations/dead-letter state is outside the Structural Seed and audit/tenant conventions

- **Evidence:** Operations is a real stateful host registering `DeadLetterDrainActor`, a reconciler, operator endpoints, subscription, and actor handlers (`src/Hexalith.EventStore.Operations/Program.cs:13-46`). Architecture Structural Seed lists Server, Admin abstractions/server/CLI/MCP/UI, AppHost, samples, and tests, but not Operations (`architecture.md:515-537`). AD-10 mentions internal/admin computation generically; no AD defines dead-letter raw-body retention, tenant identity for unidentified envelopes, replay authorization, audit identity, or deletion/erasure.
- **Scenario:** Operations evolves its app-channel token and actor store independently from Admin/gateway policy, or retains/replays a raw dead-letter containing personal data under an unidentified tenant without a governed erasure/audit rule.
- **Disposition:** **autofix**. Add Operations to the Seed/runtime topology and bind its capture/list/retry/delete semantics to AD-7, AD-9, AD-10, audit identity, retention/erasure tiers, and support-safe output.

## Low findings

### L1 - Global administrator may authorize an empty tenant

- **Evidence:** `ClaimsTenantValidator` returns Allowed for a global administrator before checking blank tenant (`src/Hexalith.EventStore/Authorization/ClaimsTenantValidator.cs:22-30`), while storage identity later throws on invalid/empty tenant (`AggregateIdentity.cs:23-38`).
- **Disposition:** **defer to implementation repair after C2**. Canonical validation must precede every role bypass; global authorization widens grant scope, not input validity.

### L2 - Claims-transformation warning can expose identity-provider parsing detail

- **Evidence:** malformed tenant/domain/permission array parsing logs the claim type plus raw parser exception text at Warning (`src/Hexalith.EventStore/Authentication/EventStoreClaimsTransformation.cs:87-105`). The claim value is not deliberately logged, but parser messages are not contractually bounded.
- **Disposition:** **defer/harden**. Emit a stable reason code and claim type only; do not pass identity-provider exception text to normal telemetry.

## Pass areas

- **NFR3 JWT posture is materially fail-closed.** Current PRD precisely fixes host set, symmetric-key rejection in Production, break-glass environment bounds, HTTPS metadata, explicit nonempty algorithm allowlist, issuer/audience/signature/lifetime validation, and clock skew (`prd.md:305-308`). This is substantially stronger than the pre-ratification posture.
- **Configuration-backed AD-25 keys are environment-gated.** Inline digest keys are accepted only in Development/Test/Testing; DAPR-secret mode forbids inline values and requires store/map/generation (`ValidateIdempotencyAdmissionOptions.cs:38-73`). The previous 2026-09-08 concern that configuration keys could be used in Production is closed in code.
- **Digest material handling is defensive.** DAPR secret fetch failures collapse to a support-safe unavailable error; the provider checks generation, loads only active/readers, and zeroes decoded buffers (`DaprSecretIdempotencyDigestKeyProvider.cs:22-82`). AD-25 also prohibits raw keys from state, downstream envelopes, and telemetry (`architecture.md:406-415`).
- **Fenced route validation is strong when it is used.** `RouteFencedCommandAsync` rejects zero/mismatched tenant/domain/aggregate/message/correlation/type context before actor invocation (`CommandRouter.cs:62-99`), and the actor validates the protected execution context (`AggregateActor.cs:4167-4179`). H5 is the parallel bypass, not weakness in this fenced branch.
- **SignalR group admission is tenant-authorized.** The hub requires authentication and validates tenant before joining a tenant/projection group (`src/Hexalith.EventStore/SignalRHub/ProjectionChangedHub.cs:84-127`).
- **AD-18 outbound header ownership is appropriately explicit.** The spine requires remove-and-replace, last-handler ownership, and negative evidence for both DAPR control-plane headers (`architecture.md:269-284`), preventing caller-forwarded routing/token confusion.
- **Health probes are explicitly separated from protected surfaces.** AD-16 names `/health`, `/alive`, `/ready` as the only support-safe anonymous exceptions (`architecture.md:243-253`); Operations exempts those exact path prefixes from its mandatory non-Development app token (`DaprAppChannelSecurity.cs:25-37`). H2 concerns the absent global default, not the probe exception.
- **Event identity and append ownership are honest about limits.** AD-5/AD-6 keep `AggregateActor` as logical append owner and stable `MessageId`/gapless aggregate sequence while explicitly refusing to claim physical write-once (`architecture.md:117-127`). C1 asks for a conforming provider profile, not for the spine to mislabel ownership as storage enforcement.
- **Projection checkpoint store contains meaningful local integrity guards.** It uses ETag-aware state reads/writes, validates checkpoint scope, protects lifecycle transitions, writes checkpoint before its active index, and exposes aggregate-scoped checkpoint erasure. The remaining H6/H7 issues are missing cross-unit normalized result and version contracts.
- **Mutation convention preserves the event record.** The spine says domain/admin/GDPR flows never edit, delete, or rewrite persisted events (`architecture.md:470`); deferred physical erasure is therefore not silently granted.

## Required disposition before a passing validation

1. Owner decision on the only conforming production actor-state profile and explicit evidence gate (C1).
2. One canonical tenant source/normalization/omission rule applied before authorization and identity derivation (C2).
3. A receiver-side application-channel credential plus mandatory fallback/endpoint allowlist across every host (H1-H2).
4. Authenticated, non-forgeable, atomic/resumable audit attribution and coordinated AD-24/AD-25 key retirement (H3-H4).
5. Resolve the adopted/current contradictions for unfenced actor mutation, AD-19 normalized results, and projection-version production ownership (H5-H7).

Until those are resolved, deterministic lint success should not be interpreted as production security or data-integrity readiness.
