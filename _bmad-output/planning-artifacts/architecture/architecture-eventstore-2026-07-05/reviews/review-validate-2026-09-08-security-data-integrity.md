## Findings

### C1 - critical - Production actor state-store provider is undecided while the only locally configured provider has a proven silent-overwrite

- **Evidence (spine):** `architecture.md:121` (AD-5: "Physical write-once enforcement remains unavailable until an approved provider-portable ETag/first-write or equivalent fence is production-path proven. Admission orchestration ... does not replace Story 4.4 publication recovery"); `architecture.md:452-458` (AD-25 names `oq8-postgresql-v1` / `state.postgresql` as the *evidence* profile only); `architecture.md:606` (Deferred: Redis `state.redis` durable write at sequence 1 "silently overwritten ... no exception ... consumed none of its one configured retry"; "no behavior is inferred for another state-store provider"); `architecture.md:486-513` (Stack table has no state-store row); `architecture.md:483` (Runtime topology convention lists component scopes but not provider).
- **Evidence (repo):** `src/Hexalith.EventStore.AppHost/DaprComponents/statestore.yaml:26` is `state.redis` with `actorStateStore: true`; `deploy/dapr/` ships both `statestore-postgresql.yaml` and `statestore-cosmosdb.yaml` as `name: statestore`; `_bmad-output/implementation-artifacts/4-5-append-durability-race-evidence.md:63` "The observed Dapr/Redis profile permits a durable same-sequence write to be lost silently".
- **Why it fails the checklist:** The AD-25 fence and the storage fence are not the same thing, and the spine says so (admission fence guards side-effect boundaries; storage fencing is deferred). So between admission and the actor's durable append there is no physical write-once guard on any provider. The spine then (a) names PostgreSQL only as an evidence profile, (b) ships CosmosDB as an equally valid `statestore`, (c) keeps Redis as the AppHost default, and (d) explicitly refuses to infer behavior for other providers. A deployment-hardening or Epic 7 story can therefore select `state.redis` (proven lossy under a second writer) or `state.azure.cosmosdb` (unproven) as the production actor state store and be fully compliant. The second-writer precondition is not hypothetical: the project memory records foreign hosts joining the fixture's DAPR placement ring through fixed non-namespaced actor type names, which is exactly the duplicate-activation scenario that turns the Redis overwrite into event loss.
- **Disposition:** discuss (provider decision is an owner call), then autofix the text.
- **Suggested wording (Stack row + Convention row + AD-5 sentence):**
  - Stack: `| Actor state store (production) | state.postgresql v1 (actorStateStore: true), oq8-postgresql-v1 profile; state.redis is Development/AppHost-only; state.azure.cosmosdb is an unproven profile that may not claim AD-5 durability until it passes the same Story 4.5 race capture |`
  - Convention `State store provider`: "The production actor state store is the provider named in the Stack table. AppHost/Development may use `state.redis`. A deployment profile that selects any other provider for `statestore` must first pass the Story 4.5 append-durability race capture and the AD-25 `oq8-*` evidence profile for that provider; until then it is non-conforming."
  - AD-5 append: "Until the deferred storage fence lands, production deployments mitigate the second-writer window by (i) the Stack-named provider only, (ii) namespaced actor types and a dedicated placement ring per environment (AD-9), and (iii) Story 4.4 recovery; none of these is write-once proof and no story may claim it."

### H1 - high - "Application-layer credential" for sidecar-to-application hops is unnamed; code already has three incompatible answers

- **Evidence (spine):** `architecture.md:149-151` (AD-10: "Public, internal, domain-service, projection-notification, and admin-computation endpoints require application-layer credentials and tenant authorization"; Prevents "endpoints trusting network location, DAPR ACLs"); `architecture.md:481` (Sidecar header convention covers *outbound* only); AD-18 `architecture.md:269-284` is outbound-only.
- **Evidence (repo):** gateway inbound: `src/Hexalith.EventStore/Authentication/DaprInternalAuthenticationHandler.cs:11-27` authenticates on the `dapr-caller-app-id` *header* against `AllowedCallers` (a header is network-location trust if the app port is reachable without the sidecar); Operations inbound: `src/Hexalith.EventStore.Operations/Security/DaprAppChannelTokenMiddleware.cs:13` validates `dapr-api-token` == `APP_API_TOKEN` (a real shared credential); DomainService SDK inbound: `src/Hexalith.EventStore.DomainService/EventStoreDomainServiceExtensions.cs` maps `/process`, `/project`, `/project/v2`, `/project/rebuild/*` with no authentication middleware, no `RequireAuthorization`, no token check (grep returned none) - it relies solely on `deploy/dapr/accesscontrol.sample.yaml` (`defaultAction: deny`, allow `eventstore` POST `/**`), i.e. exactly the DAPR-ACL-only posture AD-10 says is insufficient.
- **Why it lets two units diverge:** A domain-service story and a projection-notification story can each claim AD-10 compliance with a different mechanism (caller-app-id header, app-channel token, ACL only), and a domain service host today has none. AD-16's deny test ("a representative protected endpoint denies") is on the gateway host, not the domain-service host.
- **Disposition:** autofix.
- **Suggested wording (AD-10 numbered clause):** "Sidecar-to-application hops - gateway -> domain service (`/process`, `/query`, `/project*`), gateway -> operations, domain service/projection -> gateway callbacks - authenticate with the DAPR app-channel token: the receiving host sets `APP_API_TOKEN` and a platform-owned `ServiceDefaults` middleware rejects any non-probe request whose `dapr-api-token` does not match; `dapr-caller-app-id` and DAPR access-control policies are attribution and defense-in-depth, never the credential. `UseEventStoreDomainService()` installs that middleware; a domain-service host without a configured app-channel token fails readiness outside Development. AD-16 evidence runs on every host kind, including a domain-service host."

### H2 - high - Tenant identity has no single source-of-truth / propagation rule; omitted-tenant fallbacks already differ per surface

- **Evidence (spine):** `architecture.md:468` (State keys: tenant "remain[s] explicit in actor IDs, state keys, topic names, query scopes, SignalR groups, and admin filters" - says *where it appears*, not *where it comes from* or *who validates it*); `architecture.md:151` (AD-10 "tenant authorization" undefined); `architecture.md:404-405` (AD-25 constrains only the opaque key, not the tenant field); NFR2 `prd.md:271`.
- **Evidence (repo):** gateway validates the request tenant against `eventstore:tenant` claims (`ClaimsTenantValidator.cs:33`) *or* an actor-based validator selected by config (`ServiceCollectionExtensions.cs:119-131`); Admin.Server validates against a different claim type `AdminClaimTypes.Tenant` and, when the request omits a tenant, **falls back to the caller's first tenant claim** (`AdminBackupsController.cs:538-547`, `AdminConsistencyController.cs:148-182`); MCP tools default an omitted tenant to session context (`Admin.Mcp/Tools/ConsistencyTools.cs:22-25`); Admin.UI mints its own JWT carrying a `tenants` array from configuration (`AdminApiAccessTokenProvider.cs:143-170`); the SignalR hub does validate (`ProjectionChangedHub.cs:105-120`, pass); domain services receive tenant inside the envelope and trust the gateway (consistent with AD-3, but unstated).
- **Why it lets two units diverge:** Nothing forbids a story deriving tenant from a body/header field before authorization, or defaulting an omitted tenant to "first grant" (already done in Admin.Server) versus rejecting it (gateway). Two claim vocabularies exist. Under NFR2 a cross-tenant read via "omit tenant, get first claim" is compliant with the text as written.
- **Disposition:** autofix.
- **Suggested wording (new Convention row `Tenant identity`):** "The operating tenant is the tenant named explicitly in the request (route, envelope, or admin filter); an absent or blank tenant is rejected with a safe problem detail, never defaulted from the principal's grants, session context, or configuration. It is authorized once at the first application-layer boundary (gateway or Admin.Server) via `ITenantValidator` against the principal's tenant grants carried in the single claim type `eventstore:tenant`. Downstream hops - admission actor, `AggregateActor`, domain services, projections, SignalR groups, admin delegated writes - carry that validated tenant in the envelope/actor identity and never re-derive it from headers, claims, or defaults. Tenant `system` is reserved (NFR2)."

### H3 - high - AD-25 digest-key custody is not bound to AD-24, and the two rotation protocols are not reconciled

- **Evidence (spine):** `architecture.md:406-408,430-440` (AD-25: HMAC-SHA-256 partition digest, digest-key versions, directory flip, "Retirement is refused while records ... reference the digest-key version"); `architecture.md:384-393` (AD-24: runtime-required secrets are one logical map with a `generation` marker, `maxAge` shorter than overlap, rotation = publish-overlap-acknowledge-revoke, "then revoke the old material"); `architecture.md:480` (Secrets convention); `architecture.md:398` (AD-24 disclaims only pdenc-v2 KEK custody - silent on the admission digest key). The digest key is not in AD-24's logical-secret catalog sentence and the catalog file `deploy/dapr/openbao-secret-contract.yaml` does not exist in the repository (`ls deploy/dapr` shows no `openbao*`).
- **Evidence (repo):** two providers are selectable by config: `ConfigurationIdempotencyDigestKeyProvider` (base64 keys in `IdempotencyAdmissionOptions.DigestKeys` - i.e. app configuration) and `DaprSecretIdempotencyDigestKeyProvider` (DAPR secret map with a `generation` field, matching AD-24). Nothing in the spine or `ValidateIdempotencyAdmissionOptions.cs` forbids the configuration source outside Development.
- **Why it lets two units diverge:** (a) A deployment story can put the master digest key in configuration/Kubernetes Secret and be AD-24-compliant because AD-24 never names it as an application secret. (b) Rotation clocks conflict: AD-25 needs the *old* key material to derive retained-reader aliases until the prepare/copy/redirect/flip promotion completes for every record and tombstone; AD-24 revokes old material once runtime consumers "acknowledge the new generation while ready". If revocation follows AD-24's clock, records still addressed by the old alias become unreachable - a replayed command is then admitted as new, which is the fail-open duplicate execution AD-25 exists to prevent.
- **Disposition:** autofix.
- **Suggested wording:** AD-24 add: "The AD-25 admission digest key ring is a `runtime-required` logical secret in the OpenBao catalog (one map: `generation` + one entry per digest-key version); `IdempotencyDigestKeySource.Configuration` is Development-only and fails options validation elsewhere." AD-25 add: "Digest-key material is retrieved per AD-24. For this secret, AD-24's revoke step is gated by AD-25 retirement: the old generation is revoked only after the directory reports zero records, tombstones, aliases, migration entries, or legal holds bound to the retired version; AD-24 acknowledgement alone never authorizes revocation."

### H4 - high - "Attributable" admin mutations have no identity model or audit-record contract; caller-supplied attribution already exists

- **Evidence (spine):** `architecture.md:151` ("Admin state mutations are attributable and support-safe" - the only sentence); `architecture.md:609` (Deferred defers *audit-record deletion*, which presupposes an audit record the spine never defines); memlog `.memlog.md:29` recorded the decision "audit authenticated user/tenant/action/outcome/correlation" but it did not survive into AD-10; PRD FR34 `prd.md:241` "audit every state-mutating admin action".
- **Evidence (repo):** delegated writes forward the operator's bearer token to the gateway (`DaprBackupCommandService.cs:642-644`, `DaprProjectionCommandService.cs:112-114`) - good, the gateway sees the operator, not a service principal; but attribution is also taken from the request body: `DecisionActorId = request.OperatorActorId` (`DaprBackupCommandService.cs:255,358,379`), and `GetUserId() ?? "anonymous"` (`:491`) makes an unattributed mutation representable. `AdminProjectionRebuildController.cs:403-415` uses the authenticated `NameIdentifier` (the other interpretation).
- **Why it lets two units diverge:** One story records the authenticated `sub`, another records a body field, a third records `"anonymous"`; all three are "attributable" under the text. MCP adds a fourth actor (an LLM acting with a long-lived env-var token) with no rule on whether the audit identity is the human, the token, or the tool.
- **Disposition:** autofix.
- **Suggested wording (AD-10 clause):** "Every admin state mutation writes one audit record: authenticated principal `sub` (never a body/query field, never a placeholder), tenant, action, target identity, outcome, correlation id, timestamp, and the delegating surface (UI/CLI/MCP). Admin.Server delegates writes to the gateway with the operator's own bearer token; it never substitutes a service principal or synthesizes an actor id. A mutation whose principal cannot be resolved is rejected, not recorded as anonymous. Audit records are append-only read-model state under AD-7 and are excluded from AD-7 erasure (deletion is deferred per the Deferred table)."

### H5 - high - Deny-by-default is described as conditional; a new controller is fail-open by construction

- **Evidence (spine):** `architecture.md:249` (AD-16.3: "any host that introduces a global fallback authorization policy ... introduces the explicit probe-anonymity contract in the same or an earlier slice" - the fallback is treated as optional); `architecture.md:253` (evidence = "a representative protected endpoint ... denies"); `architecture.md:473` (Health probes convention presumes a fallback exists).
- **Evidence (repo):** `grep FallbackPolicy src/` returns nothing; the gateway relies on per-controller `[Authorize]` (`CommandsController.cs:20`, etc.) and `services.AddAuthorization()` with no default/fallback policy (`ServiceCollectionExtensions.cs:103`); the generator emits `[Authorize]` per controller (`RestApiControllerEmitter.cs:221`); minimal-API groups exist without authorization metadata (`OpenApi/ErrorReferenceEndpoints.cs:149-164`, intentionally public catalog; runtime-proof endpoints are Development-gated).
- **Why it fails the checklist:** AD-10 says security fails closed, but the mechanism that makes *omission* fail closed is optional. A story adding a controller or minimal-API map without `[Authorize]` is compliant and anonymous. AD-16's single-endpoint evidence cannot detect that.
- **Disposition:** autofix.
- **Suggested wording (AD-16.3 replace "any host that introduces" with a requirement):** "Every EventStore host (gateway, Admin.Server, domain-service hosts, Operations, external API hosts, Admin.UI) sets `AuthorizationOptions.FallbackPolicy = RequireAuthenticatedUser` through `ServiceDefaults`; per-endpoint `[Authorize]` narrows, it never establishes. Anonymous endpoints are an explicit allowlist: the three probes (AD-16) and the static `/problems` error catalog. AD-16 evidence adds a structural scan that fails when a host maps any endpoint outside that allowlist without authorization metadata."

### M3 - medium - Erasure has three meanings and no tiering; two stories can claim different completeness

- **Evidence (spine):** `architecture.md:133` (AD-7: erasure = selected read-model keys + companion delivery/rebuild/checkpoint keys, one logical scoped operation); `architecture.md:374-376` (AD-23: `IPersonalDataPolicy`, `IErasureStateProvider` seams, "Parties retains ... erasure orchestration semantics"); `architecture.md:609` (Deferred: full aggregate/event tombstoning, broker-history deletion, backup erasure, audit-record deletion out of MVP); `architecture.md:479` (Payload protection convention).
