# Architecture validation · independent implementation review

The spine leaves three high-severity conflicts and one medium-severity ordering ambiguity. The conflicts affect Tenants bootstrap, erasure-verifier custody and consumer-removal evidence. This review covers the full November 21 spine, SHA-256 `7ad8fe0af4e9eb42903b3a2d08577b07eef21112f2a9f8a8a64fd01c15a921f6`, on EventStore source `df5dc226a`. The checks below compare the decisions with frozen contracts, source, and existing test assertions. [Reviewed spine](../../../architecture.md)

## High · The bound platform command requires two independently checked identities

AD-18 lines 285–288 instruct the outbound handler to remove the human credential on every workload request. AD-36 line 433 instructs the receiver to reject both kinds together. Applied literally by one host, this prevents another host from completing the Story 2.14 bound platform command. That operation separately authenticates the human and matches the subject to the bound requester after workload authorization. Ordinary workload calls retain credential exclusivity. The exception is exercised by the existing authentication tests. [2.14 hosted decision, line 120](../../../../../_bmad-output/implementation-artifacts/spec-2-14-canonical-tenant-boundary.md) · [Command controller, lines 94–125](../../../../../src/Hexalith.EventStore/Controllers/CommandsController.cs) · [Authentication tests, lines 53 and 116](../../../../../tests/Hexalith.EventStore.Server.Tests/Authentication/DaprInternalAuthenticationHandlerTests.cs)

Reconcile the diagram and both ADs with the single bound route. Distinguish the workload identity that authorizes the hop from the independently authenticated human that binds the command. Keep the existing ordinary-route rejection and the host evidence requirements.

## High · The erasure verifier has two incompatible key-custody assignments

AD-24 line 326 assigns every internal proof, expressly including the trusted-effect erasure capability, a dedicated key outside the AD-25 digest ring. The 4.16 status entry at line 600 points to the accepted extension of the existing HMAC verifier. The owning contract requires that verifier to use the existing key-ring generations and recognizes its signing capability. The implemented capability takes the idempotency digest-key provider. A secrets owner following AD-24 can provision a different generation from the one the verifier accepts, or a retirement owner can omit an active verifier from the consumers of the existing generation. [Approved 4.16 contract, lines 71 and 85–87](../../../../../_bmad-output/implementation-artifacts/spec-4-16-append-write-once-conformance-through-enforced-envelope.md) · [Capability source, lines 12, 29–34 and 65](../../../../../src/Hexalith.EventStore.Server/Commands/TrustedEffectErasureCapability.cs)

Distinguish the future dedicated-key rule from the approved erasure-verifier contract. State which generation and consumer acknowledgments protect retirement during any transition. Security, Platform and Story 7.6 still owe the named custody and behavior qualification before distribution.

## High · The consumer-removal rule lacks a join between package and host subjects

AD-22 line 312 requires “the same immutable subject” from package capability through production promotion. AD-11 line 224 requires a Platform-composed host to start its own chain and limits EventStore issuance to the package subject. A consumer verifier using one subject identifier throughout rejects a correctly composed deployment. Treating a package receipt as host evidence invalidates the separate Platform issuance contract. The publication contract binds the promoted host to the precise package artifacts and keeps the two chains distinct. [Subject types and record ownership, lines 34–41](../../../../../docs/architecture/publication-authority-v1.md) · [Deployment and package binding, lines 185–195](../../../../../docs/architecture/publication-authority-v1.md) · [PRD publication and consumer decisions, §11.4](../../../prd.md)

For a shared host, require a consistent subject within each chain. Join the released EventStore package to the Platform host through the exact package identity in the promoted profile. The consumer owner’s removal receipt then binds that deployment and the separate consumer revision and removal subject. Missing links keep G-CONSUMER blocked. This clarification leaves the existing assurance and production gates in force.

## Medium · A global reservation gap can be mistaken for a missing aggregate event

AD-6 line 169 requires a nonzero global position and a gapless aggregate sequence. It omits the frozen allocator’s cross-aggregate contract. Its separate actor reserves a contiguous range for a command before the aggregate commits. A failed downstream commit can therefore leave a permanent gap between committed global positions. A reader that waits for every intervening global position and a reader that tolerates unused reservations both satisfy the current sentence, but the former cannot advance past such a gap. [Frozen ordering contract, lines 17, 31–32 and 71](../../../../../_bmad-output/implementation-artifacts/spec-dapr-global-event-ordering.md) · [Allocator, lines 20–36](../../../../../src/Hexalith.EventStore.Server/Actors/GlobalPositionActor.cs)

State that global positions are unique and allocated monotonically in contiguous per-command ranges. Readers must tolerate unused ranges. Gapless sequence checks apply to the addressed aggregate. FR24 still requires owner approval of a successor specification before any sharding implementation.
