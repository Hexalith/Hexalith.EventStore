## High

### H1 — No rule separates human-delegated gateway relays from internal workload calls (AD-36, AD-18, AD-28, Design Paradigm diagram)

- **Locator:** `architecture.md:394` (AD-36 "Every service-to-service call into a protected EventStore or domain-service endpoint presents … exactly one short-lived workload assertion"); `:256-257` (AD-18 "Internal workload calls never forward an inbound `Authorization` bearer"); `:342` (AD-28 "Every non-Development DAPR app endpoint validates `dapr-api-token` … service-invocation operations additionally require an AD-36 workload assertion"); `:72` (diagram `Client … -->|public HTTP|`) vs `:488` (`TenantsApi -->|service invocation only| ES`). Brownfield: `samples/Hexalith.EventStore.Sample.Api/Program.cs:30-39`, `Admin.UI/AdminUIServiceExtensions.cs:106-119`, and `Sample.BlazorUI/Program.cs:65` reach their targets through Dapr service invocation and forward the human bearer. The gateway selects its scheme by assertion-header presence (`Extensions/ServiceCollectionExtensions.cs:87-90`).
- **Finding:** Generated API hosts (AD-4, which delegate through `IEventStoreGatewayClient`), the Sample UI and API, the Tenants API, and Admin UI → Admin Server all make service-to-service calls into protected endpoints over Dapr service invocation. Read literally, AD-36 and AD-28 require each of these calls to carry a workload assertion, and AD-18 forbids forwarding the bearer. Followed that way, either every human-authorized external call is denied (a workload principal "never satisfies a human-authorization policy"), or human authorization is dropped. The brownfield, and the in-flight Story 5.5 code, keep the bearer and send no assertion, which is non-conformant to the letter of three adopted rules. AD-28's "every DAPR app endpoint" also never says whether a public controller reachable both through ingress and through the app channel is a "DAPR app endpoint". Story 5.11 and every generated-host author will resolve this differently.
- **Proposed fix:** Add to AD-36 (and cross-reference it from AD-18 and AD-28) two named call classes. (a) A *human-delegated relay*: a platform gateway client forwards only the end-user bearer, carries no workload assertion, and is authorized under AD-10 human policies at the receiver. (b) A *workload call*: it carries exactly one assertion and never a bearer. A request that presents both is denied. Scope AD-28's channel-token check to routes the platform maps as Dapr-delivered, and correct the diagram edge at `:72` to show relay-via-service-invocation.

### H2 — The adopted AD-16 fallback policy is absent on every brownfield host but one, and only an unowned narrow row records it (AD-16, AD-28, gate row `:529`)

- **Locator:** `architecture.md:230` (AD-16 "Every HTTP host configures an authenticated fallback authorization policy … Only `/health`, `/alive`, and `/ready` carry explicit `AllowAnonymous`"); `:342` (AD-28 "Routes admitted by the channel alone … remain under AD-16's authenticated fallback"); `:529` (gate row covering only `MapSubscribeHandler`/`MapActorsHandlers`, "No owner yet"). Brownfield: no `FallbackPolicy` in the EventStore gateway (`Extensions/ServiceCollectionExtensions.cs:111` sets only `DefaultPolicy`), Admin Server, Admin UI, Sample API, Sample Blazor UI, or Operations. The UI hosts map `MapStaticAssets()`/`MapRazorComponents()` anonymously (`Admin.UI/AdminUIServiceExtensions.cs:183-188`, `Sample.BlazorUI/Program.cs:77-78`). `epics.md:4206` (Story 5.3) explicitly "does not introduce a new global fallback authorization policy".
- **Finding:** AD-16 is `[ADOPTED]`, and no story owns implementing it. The one gate row covers two framework routes and has no owner. The rule also never says which authentication schemes satisfy the fallback. On the gateway the default policy is human-only JwtBearer, so a human-only fallback would deny Dapr pub/sub and actor callbacks that AD-28 says "remain under" it. The DomainService SDK instead uses "any workload". For interactive UI hosts, a rule allowing exactly three anonymous endpoints cannot be satisfied without a login flow, and PRD §9.2 keeps Admin interactive OIDC login out of MVP. That is a PRD/spine tension the spine does not surface.
- **Proposed fix:** Widen gate row `:529` to "AD-16 fallback policy on every HTTP host", name an owner story or route it to correct-course, and list the non-conforming hosts. Add one AD-16 sentence defining the fallback as "deny unless the endpoint names a policy". Each policy then names its scheme: human JwtBearer, AD-36 workload, or AD-28 sidecar channel. Record the UI-host static-asset and login conflict with PRD §9.2 as an open item for the product owner. Do not invent an exemption.

### H5 — Best-effort ETag regeneration can produce false `304 Not Modified` responses, and the recommended open question was dropped (AD-8, AD-14)

- **Locator:** `architecture.md:160` (AD-8 "`Direct` … one Dapr actor invocation plus local broadcast with no redelivery … neither a signal nor its absence is completion or freshness evidence"); `:218` (AD-14 ETag is platform metadata). Brownfield: `Server/Actors/EventReplayProjectionActor.cs:62-80` (regeneration fails open); `Controllers/QueriesController.cs:134-173` (a `304` is decided from the ETag-actor value). Memlog `:172` open question (2); `reconcile-update-2026-10-07-story-5-5.md:171,195` ("Record OQ-1, OQ-2, and OQ-6 in the Implementation Status table"). OQ-1 and OQ-6 landed (`:537`, `:529`); OQ-2 did not.
- **Finding:** AD-8 declares ETag regeneration a best-effort hint, while the gateway uses that same ETag as the sole validator for `304`. A `304` asserts the representation is unchanged. After one lost regeneration under the default, production-eligible `Direct` transport, clients get `304` for changed data until the next change. They cannot "tolerate" this, because they never see the change. No gate row, owner, or safe posture exists.
- **Proposed fix:** Add a gate row: "Stale `304` after a lost ETag regeneration under `Direct` (AD-8/AD-14)". Its safe posture is no freshness claim from gateway `304`. Its owner and trigger should be explicit, for example a test-first story or correct-course. Alternatively, add an AD-14 sentence: "A gateway `304` is emitted only from a validator derived from persisted read-model/checkpoint state or from a durably retried regeneration."

### H6 — Channel-only Dapr routes cannot tell sidecar delivery from peer invocation, and the open question was dropped (AD-28, AD-9)

- **Locator:** `architecture.md:342` (AD-28 "Routes admitted by the channel alone (subscription discovery, pub/sub delivery, actor callbacks) confer no workload identity, operation, tenant, or administrator authority"); memlog `:172` question (4); `reconcile-update-2026-10-07-story-5-5.md:176` (OQ-5). Brownfield: `deploy/dapr/accesscontrol.yaml:32-42` grants `eventstore-admin` `/**` on `eventstore`, which includes `/actors/**` and the subscription routes.
- **Finding:** The receiving sidecar adds `APP_API_TOKEN` to every inbound call. Any ACL-permitted peer can therefore reach pub/sub delivery and actor-callback routes through service invocation, and those routes perform effects: projection updates, ETag regeneration, and actor methods. AD-28's "confer no authority" cannot be enforced in the application, and no ACL rule or gate row closes the gap. Story 5.7 (ACL parity) and Story 5.5 can each assume the other owns it.
- **Proposed fix:** Add to AD-9 or AD-28: "Deployment ACLs deny service invocation of subscription, pub/sub-delivery, and actor-callback paths for every caller." Add a gate row with Story 5.7 as owner, a negative peer-invocation proof, and a safe posture of no FR28/NFR1 internal-slice readiness claim.

### H7 — The production identity issuer and the global-administrator bootstrap are missing from the operational envelope (AD-36, AD-26, AD-10, AD-24)

- **Locator:** `architecture.md:394` (AD-36 "names one caller workload, the receiver's AD-33 app ID as audience, and the one operation … never broadened across audiences or operations"); `:396` (only resource binding is flagged non-production); `:330` (AD-26 profile digest bind list, with no issuer); `:528` (gate row). `spec-5-5-…:169` (BH-1: the authority-mode client-credentials token is cached and ignores audience and operation); `:177` and `:212` (BH-9/EC-18: no production administrator bootstrap credential); reconcile OQ-4 (IdP lifetime ceilings) and OQ-8.
- **Finding:** AD-36 requires per-audience, per-operation, short-lived assertions on every internal production call. No authority-mode issuance path has been shown to narrow tokens that way, and the in-flight implementation cannot. The spine flags only the narrower pub/sub resource binding as non-production. Neither the production IdP or issuer, its per-workload client registrations, its lifetime-ceiling compatibility, nor the production global-administrator bootstrap credential is decided or deferred with an owner. The AD-26 profile digest binds neither the issuer nor the AD-10 host fingerprint inventory. This is an unaddressed dimension of the deployment envelope.
- **Proposed fix:** Add the production OIDC issuer identity, its per-workload client and scope mapping, the assertion lifetime ceiling, and the AD-10 fingerprint inventory digest to the AD-26 profile bind list. Add a gate row: "Production workload-assertion issuer qualification and administrator bootstrap". Its owner is Security with Story 5.5/5.11; its safe posture is no production internal-call claim. Alternatively, mark AD-36's per-operation clause `[ASSUMPTION]` until an issuer qualifies.

### H8 — The adopted ban on reading Dapr private actor-state keys is contradicted by production Admin code and is missing from AD-34's non-conformance list (AD-1, AD-3, AD-34)

- **Locator:** `architecture.md:114` (AD-1 "application code never reads or writes Dapr private actor-state keys"); `:126` (AD-3 "permits neither … reads of Dapr private actor-state keys/tables"); `:382` (AD-34 "Current state" names only the Redis backplane and payload key operations). - **Finding:** The spine records two non-conformances in a way that reads as complete. Story 3.17's inventory and later Admin work can treat this third one as existing, accepted behavior. It crosses the actor boundary that AD-1, AD-3, and AD-13 make the sole authority.
