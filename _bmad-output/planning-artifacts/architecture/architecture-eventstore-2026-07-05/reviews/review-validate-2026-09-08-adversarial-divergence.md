### C1 - Tenant identity has no canonical source or normalization rule; the tree already holds three incompatible readings (critical)

**Evidence (spine).** The State-keys convention only says tenant identity "remain[s] explicit in actor IDs, state keys, topic names, query scopes, SignalR groups, and admin filters" (`architecture.md:468`). AD-10 requires "tenant authorization" (`:151`), AD-25 partitions admission "by managed tenant" (`:406`), AD-7 scopes erasure "tenant/domain/aggregate/projection" (`:133`), AD-8 scopes sequence guards the same way (`:139`). No AD names the tenant-identity source (claim vs route vs fixed) or a canonical string form (case, trimming, allowed alphabet).

**Evidence (tree).**
- `src/Hexalith.EventStore.Contracts/Identity/AggregateIdentity.cs:28-29` force-lowercases tenant and domain and reject uppercase by regex; actor IDs, event-stream, metadata and snapshot keys are built from the lowercased form.
- `src/Hexalith.EventStore/Authorization/ClaimsTenantValidator.cs:44-45` compares the command's tenant to `eventstore:tenant` claims with `StringComparison.Ordinal` ("tenant IDs are system-assigned").
- `src/Hexalith.EventStore/Authorization/AdminTenantAuthorizationFilter.cs:46-49` compares the raw route/query value ordinally to claims.
- `src/Hexalith.EventStore.Admin.Server/Services/DaprProjectionQueryService.cs:77-79,205-206` compares tenant ids `OrdinalIgnoreCase` and introduces a `TenantAllSentinel`.
- `src/Hexalith.EventStore/SignalRHub/ProjectionChangedHub.cs:79-82` and `SignalRProjectionChangedBroadcaster.cs:149` build group names from the raw `tenantId` string; a client joining `Proj:Acme` never receives a broadcast keyed `Proj:acme`.
- `src/Hexalith.EventStore.Contracts/Rest/RestTenantSource.cs` offers `Claims | Route | System`; the generated controller returns the literal `"system"` or the raw route value (`RestApiControllerEmitter.cs:409-430`), with no normalization.

**Divergence pair.** Unit A = Story 7.2 "Admin claims normalization ... exactly like gateway claims", whose AC says items are "canonicalized, deduplicated ordinally" - it freezes ordinal, case-preserving canonical tenant claims and cites AD-3/AD-10/AD-12. Unit B = Story 4.7 / the Story 1.9 lineage adopting canonical read-model addresses `readmodel:{tenant}:...` built from `AggregateIdentity` - it freezes lowercase tenant segments and cites AD-7/AD-14/AD-15. Both are letter-compliant. Result: a principal with claim `Acme` is authorized for tenant `Acme`, its events and read models live under `acme`, its SignalR freshness group is `Acme`, Admin tenant filters match either, and the AD-25 admission partition uses whichever string the adapter passes. Tenant isolation (AD-10) and "one logical tenant-scoped operation" (AD-7) are then true per unit and false across units.

**Disposition: autofix (new convention row + AD-10 clause).** Suggested wording, Consistency Conventions table:

> | Tenant identity | The tenant of every request is exactly one value: the authenticated principal's normalized `eventstore:tenant` claim that matches the request's declared tenant, or the fixed `system` tenant for `RestTenantSource.System`. Canonical form is the `AggregateIdentity` form (lowercase, `[a-z0-9-]`, no colon); every comparison, actor ID, state key, SignalR group, admin filter, admission partition, and audit record uses that canonical form, produced by one platform normalizer in `Contracts`. Hosts do not add case-insensitive or sentinel matching. |

and append to AD-10's Rule: "Tenant authorization compares canonical tenant identity only; a request whose declared tenant does not normalize to an authorized claim is denied before any state access."

### H1 - Correlation identity is load-bearing (AD-17 status key) but its generation, validation, and propagation are unowned; Story 5.4 is about to define an Admin-local rule (high)

**Evidence (spine).** AD-17 item 3 makes `CorrelationId` the single gateway-owned command-status tracking key (`:263`). The Identity convention says correlation identifiers "use ULID-safe handling where envelope semantics require sortable ids" (`:466`) but names no header, validator, generator, or propagation rule, and nothing says whether the HTTP `X-Correlation-ID` is such a field. No AD covers trace/metric/log naming or correlation propagation at all (surface h).

**Evidence (tree).** Gateway middleware `src/Hexalith.EventStore/Middleware/CorrelationIdMiddleware.cs` accepts `^[a-zA-Z0-9]([a-zA-Z0-9-]*[a-zA-Z0-9])?$` up to 128 chars and mints a sortable ULID; Admin host middleware `src/Hexalith.EventStore.Admin.Server.Host/Middleware/CorrelationIdMiddleware.cs:12-20` accepts only `Guid.TryParse` and mints a GUID (the forbidden API per `:466`). W3C `traceparent` is separately carried as a `SubmitCommand` extension (`src/Hexalith.EventStore.Server/Commands/SubmitCommandExtensions.cs:13`). `ServiceDefaults/Extensions.cs:29-33` subscribes ActivitySource `Hexalith.EventStore` while domain hosts emit `Hexalith.EventStore.Domain.{domain}` (`EventStoreDomainTelemetry.cs:14-21`).

**Divergence pair.** Unit A = Story 5.4 (in review) AC: the Admin middleware "preserves only an accepted value ... under the documented compatibility rule" - it documents its own rule (e.g. ULID or GUID-compat, underscore allowed) citing AD-10 and `:466`. Unit B = Story 7.3 audit intent, which persists "ULID-safe correlation" and must join to the gateway's command status by AD-17's `statusKey`. When Admin accepts a token the gateway regex rejects (or vice versa), the gateway silently mints a new id, and the audit row, the `202` `Location`, and the trace never share one key. Both units obey every AD.

**Disposition: autofix.** Add to the Identity convention row (`:466`): "The request correlation identifier is the `X-Correlation-ID` header. One platform validator in `Contracts` (ULID canonical; bounded legacy token compatibility defined once) is used by every host; every host mints a ULID when the inbound value is rejected, echoes it on the response, forwards it unchanged on every gateway, domain-service, and Admin hop, and records it as `CorrelationId` in envelopes, command status (AD-17), audit records, and logs. `traceparent` propagation is additive and never replaces it." Add a Telemetry row: "ActivitySource and Meter names are `Hexalith.EventStore` (platform) and `Hexalith.EventStore.Domain.{domain}` (domain hosts); ServiceDefaults subscribes both; story specs may add metric names only under those prefixes."

### H2 - AD-25 admission adapters, digest-key versions, and retention classes are per-host / per-adapter choices with no deployment-wide catalog owner (high)

**Evidence (spine).** AD-25 says "a registered server-trusted adapter supplies a versioned canonical-intent descriptor and fixed retention class" (`:404`), partitions the actor by "digest-key version" (`:406-407`), and says the directory runs "on every compatible host" and "Mixed software versions that do not implement directory routing are deployment-incompatible and fail readiness" (`:428-438`). Nothing states that the *active* digest-key version, the retained-reader set, the retention-class catalog, or the adapter registry key is a single deployment-wide catalog rather than a host-local choice.

**Evidence (tree).** `IdempotencyAdmissionOptions.ActiveDigestKeyVersion` / `ReaderDigestKeyVersions` are per-host configuration (`Server/Configuration/IdempotencyAdmissionOptions.cs:13-16`). The adapter registry is keyed by the bare `CommandType` string with no domain segment (`Server/Commands/IdempotencyIntentAdapterRegistry.cs:30-52`), and each adapter chooses its own `DescriptorVersion` and `RetentionTier` (`DomainService/IIdempotencyIntentAdapter.cs`). The retention catalog is the two-member enum `IdempotencyReplayRetentionTier { Mutation, Commit }` in `Contracts`.

**Divergence pairs.**
- Rotation: Host A (Story 4.13-style rotation slice) is configured active=`v2`, readers=`[v1]`; Host B (an older or differently configured replica) is active=`v1`, readers=`[]`. Both implement directory routing, so both pass the `:437` readiness rule. A key first admitted on A creates a `v2` canonical record; the same key presented to B derives aliases `v1` only, finds no record, and creates a fresh `v1` authority - the "single prior authority" guarantee (`:436`) holds per host and fails across hosts.
- Adapters: Sample registers `CommandType="Create"` (`DescriptorVersion=1`, `Mutation`), Tenants registers `CommandType="Create"` (`DescriptorVersion=3`, `Commit`) in the same gateway. Startup throws "Multiple trusted idempotency adapters are registered for one command type" - fail-closed, but the spine does not say the key is `(Domain, CommandType)` as AD-19 does for projections (`:290`), so a story that "fixes" it by namespacing one side changes descriptor bytes and therefore intent-comparison outcomes for replays.

**Disposition: autofix.** Amend AD-25: "The active digest-key version, the ordered retained-reader set, the retention-class catalog, and the adapter registry are one deployment-wide catalog owned by the platform deployment overlay (the same owner as AD-24's secret contract) and validated at readiness on every host; a host whose active/reader set differs from the catalog fails readiness. Adapters are registered by `(Domain, CommandType)`; `AdapterId`, `OperationId`, and `DescriptorVersion` are recorded in the catalog and a change to any of them is a new descriptor version, never a silent re-registration."

### H3 - Production actor state-store provider is not decided: PostgreSQL is the only proven profile, yet Cosmos DB ships as "production" and Redis is the local topology (high)

**Evidence (spine).** AD-25 fixes the evidence profile `oq8-postgresql-v1` (`state.postgresql`, `actorStateStore: true`, `deploy/dapr/resiliency.yaml`, two hosts) (`:450-455`). Deferred records the Redis silent-overwrite defect and says "no behavior is inferred for another state-store provider" (`:606`). AD-9 makes topology one unit (`:145`); AD-24 requires component `secretKeyRef` (`:384`). No AD says which provider(s) are conforming for production actor state, or that a deployment profile must use the OQ8-proven provider.

**Evidence (tree).** `deploy/dapr/statestore-postgresql.yaml` and `deploy/dapr/statestore-cosmosdb.yaml` are both labelled production in `deploy/README.md:10-11,29-31`; AppHost local is `state.redis` (`src/Hexalith.EventStore.AppHost/DaprComponents/statestore.yaml:26`); `ProductionDaprComponentValidationTests.cs:201-209` asserts only that the Cosmos component is named `statestore` and has `actorStateStore`. The Cosmos component carries `masterKey: "{env:COSMOSDB_KEY}"` inline (`statestore-cosmosdb.yaml:27-29`), which is already non-conforming with AD-24's `secretKeyRef` rule.

**Divergence pair.** Unit A = Stories 4.14/4.15 assemble the OQ8 packet on PostgreSQL and declare AD-25 admission serialization, fencing, and compaction proven (AD-12 `:171`). Unit B = a Story 7.9 / ACA-adjacent deployment slice ships the Cosmos DB overlay, changes AppHost + YAML + topology tests together (AD-9), routes its key through `openbao` (AD-24), and cites the Unit A packet as its AD-12 evidence because the spine calls that packet "production-equivalent". Cosmos's actor transaction/ETag semantics were never exercised; the Redis overwrite class of defect (`:606`) is exactly the class the packet cannot speak to for another provider.

**Disposition: autofix.** Add to AD-25 (or a new AD-26 "Actor state-store provider is evidence-bound"): "The production actor state store is exactly the provider of the approved evidence profile (`state.postgresql`). Any other provider - including `state.azure.cosmosdb` and `state.redis` - is non-production until an equivalent AD-12/AD-25 packet is assembled on that provider and approved; deployment overlays may not label an unproven provider as production, and topology tests assert the provider type, not only the component name." Separately route the inline-`masterKey` non-conformance to the AD-24 deployment story.

### H4 - `ProjectionVersion` has a source (AD-15) but no meaning or owner; projection handlers and UI evidence-state consumers can disagree (high)

**Evidence (spine).** AD-15 item 3: `ProjectionVersion` is authoritative only when sourced from `IReadModelFreshness` (`:235`). AD-14 says "ETag and projection version are distinct unless a projection explicitly defines them as equivalent" (`:198`). AD-20 requires rebuild "projection versions, and checkpoints must equal canonical aggregate replay" (`:315`). AD-7 speaks of "companion delivery/rebuild sequence or checkpoint keys" (`:133`). Nothing says what a `ProjectionVersion` *is* (aggregate sequence? projection-scoped checkpoint? global position? opaque?), who assigns it, or whether it is comparable across projections.

**Evidence (tree).** `IReadModelFreshness.ProjectionVersion` is a free `string?` (`Client/Projections/IReadModelFreshness.cs:34`). Tenants derives it as a prefix plus the aggregate sequence (`references/Hexalith.Tenants/src/Hexalith.Tenants/Projections/TenantProjectionHandler.cs:246`), and its UI compares baseline vs observed versions (`Tenants.UI/State/TenantCommands/TenantLifecycleAttemptTracker.cs:305-313`). EventStore's checkpoints are projection-scoped `projection-checkpoints:{ActorId}:{projectionName}` (`Server/Projections/ProjectionCheckpointTracker.cs:20,609`); read-model batch markers use `hxrmb:v1:marker:` (`Client/Projections/ReadModelBatchKeys.cs:9`); Admin copies the command-status key format locally (`Admin.Server/Helpers/AdminStateStoreKeys.cs`).

**Divergence pair.** Unit A = Story 4.7 keeps Tenants' `"tenant-agg:{sequence}"` form for `ProjectionBacked` routes (AD-14/AD-15 compliant: sourced from persisted freshness, not aliased from ETag). Unit B = Story 7.19 (Admin typed-client + evidence-state UI) or a Story 6.x checkpoint optimisation renders "current version vs projection checkpoint" for every domain by reading the projection-scoped checkpoint, expecting a monotonic per-projection value. For Tenants the two values are incomparable; AD-20's "versions equal replay" is untestable because no unit knows which value replay should reproduce.

**Disposition: discuss, then autofix.** Recommended clause in AD-15 or AD-20: "`ProjectionVersion` is the platform-defined monotonic version of the `(tenant, domain, aggregate, projection)` read model: the last applied aggregate sequence for aggregate-scoped models and the last applied delivery checkpoint for shared/index models, rendered by one platform formatter; producers do not invent alternate encodings. Companion checkpoint, marker, rebuild, and command-status state keys are owned by `Server` (schemes in `ProjectionCheckpointTracker`, `ProjectionRebuildCheckpointStore`, `ProjectionReadModelAddressFactory`); `Client` and `Admin` consume those schemes through platform seams and never restate them locally."

### H5 - Admin delegated writes: the attributable subject at the gateway is unspecified (operator pass-through vs Admin service principal) (high)

**Evidence (spine).** Paradigm and topology diagrams show Admin Server doing "delegated writes and safe reads" / "state-mutating actions" to the gateway (`:78`, `:577`) and "support-safe operational reads only" against the state store (`:576`). AD-10 requires "Admin state mutations are attributable and support-safe" (`:151`). AD-21 fixes the UI-to-Admin typed client (`:321`); AD-18 makes only the DAPR routing headers handler-owned (`:271-284`). No AD says whose identity crosses Admin -> gateway.

**Evidence (tree).** Admin.Server forwards the operator's bearer token verbatim on every gateway call (`Admin.Server/Services/HttpContextAdminAuthContext.cs`, `DaprProjectionQueryService.cs:109-112`, `DaprHealthQueryService.cs:96`, `DaprTenantQueryService.cs:207`). Story 7.3 AC requires a durable Admin-side audit intent with "authenticated subject ... ULID-safe correlation" persisted before any side effect; Story 5.5 owns the internal/domain-service trust boundary; Story 7.5 the shared typed Admin client.

**Divergence pair.** Unit A = Story 7.3: audit identity is the operator; to make continuation work durable after the operator's token expires it calls the gateway with an Admin service credential (provisioned per AD-24) and an `X-Hexalith-On-Behalf-Of` envelope field. Unit B = Story 5.5 gateway trust boundary: the gateway's attributable subject is the presented bearer token's `sub`, and it rejects (fail-closed, AD-10) any caller-supplied on-behalf-of claim as "caller-supplied administrator flags" (`:149`). Both obey AD-10/AD-12/AD-21/AD-24. Outcome is either every delegated write denied, or - if the gateway accepts the service principal - two persisted audit trails naming different actors for one mutation.

**Disposition: autofix.** Add to AD-10 (or AD-21): "Admin Server, CLI, and MCP hold no standing gateway credential. Every delegated write presents the operator's own current bearer token unchanged, so the gateway's attributable subject, the command envelope's user identity, and the Admin-side audit subject are the same principal and share one correlation identifier (H1). A service-principal or on-behalf-of path requires a separate AD before any story implements it."

### H6 - Erasure completeness has two authorities: AD-7 read-model/checkpoint erasure and AD-23 `IErasureStateProvider` key invalidation; rebuild after key invalidation conflicts with AD-19/AD-20 (high)

**Evidence (spine).** AD-7: "Erasure removes selected read-model keys and companion ... checkpoint keys as one logical tenant/domain/aggregate/projection-scoped operation" (`:133`). AD-23 gives EventStore the `IErasureStateProvider` seam and Parties "erasure orchestration semantics" (`:374`); AD-25 forbids protected intent in evidence (`:408-410`). Deferred keeps full aggregate/event tombstoning out of scope (`:610`). Nothing orders or couples the two erasure mechanisms, or says what a projection does with events it can no longer decrypt.

**Evidence (tree/specs).** Story 1.9 ships coordinated read-model + checkpoint erasure via a `ProjectionLifecycleActor`, returns `Unsupported` where no canonical writer exists, and accepts a TOCTOU write-after-erase residual (spec-1-9 D1/D3). The payload-protection spec makes erasure a keyed per-domain `IErasureStateProvider` state machine (`Pending/Invalidating/Invalidated/Deleted`, spec lines 937-951), defines per-scope erasure as wrapped-DEK deletion (lines 1370-1375), and says projection/rebuild paths take "No checkpoint advance for unreadable input" (line 2158).

**Divergence pair.** Unit A = Story 8.5/8.7: erasure for a scope = key-record invalidation; the Parties certificate reads "online access invalidated". Plaintext read models projected from that scope (AD-7's territory) are untouched because they are not ciphertext. Unit B = Story 1.9 lineage / Tenants: erasure = read-model + checkpoint deletion; events untouched; reports `Success`. Both compliant; neither is complete, and no single state says whether the scope is erased. Second-order conflict: after Unit A invalidates keys, any AD-20 paged rebuild that reaches that aggregate's events gets an unreadable payload, AD-19 normalizes it to `Indeterminate/NotAdvanced`, and the projection stays `Rebuilding` forever - AD-20's "promotes ... only after all required projections complete" can never be satisfied.

**Disposition: discuss (cross-repo with Parties), then amend AD-7/AD-23.** Proposed: "A scope's erasure state has one authority: the registered `IErasureStateProvider` for that domain. AD-7 read-model/checkpoint erasure for the scope is a required, ordered step before the scope may transition to `Invalidated`, and the lifecycle actor records it in the same operation. Projection delivery and rebuild treat events of an `Invalidated`/`Deleted` scope as an explicit `Erased` outcome that advances the checkpoint without producing read-model state; `Indeterminate` is reserved for transient failure."

### M1 - Host-to-domain ownership is a convention (`appId ?? command.Domain`), and `(Domain, ProjectionType)` uniqueness is not bound across hosts (medium)

**Evidence.** AD-2 (`:103`), AD-9 (`:145`), and AD-19 (`:290`: "A domain may register multiple named handlers") never state that one domain maps to exactly one app-id or that a `(Domain, ProjectionType)` route is served by exactly one host. `DaprDomainServiceInvoker.cs:108,137` falls back to `appId = command.Domain`; `DomainServiceRegistration` is `(AppId, MethodName, TenantId, Domain, Version)`; the named projection catalog dedupes only on `(AppId, ServiceVersion, Domain)` (`NamedProjectionRouteCatalogSnapshot.cs:20-23`), so two app-ids can both bind `(tenants, TenantList)`. AD-19 then requires "exactly one entry for each admitted `(Domain, ProjectionType)`" (`:292`) and normalizes a duplicate outcome to `Indeterminate/NotAdvanced` (`:305`).

**Pair.** Unit A hosts domain `tenants` in app `tenants`; Unit B (an Epic 6/7 projection-offload story) hosts only the `TenantList` handler in app `tenants-projections`, both "domain-centric" per AD-2 and both changing AppHost + YAML per AD-9. Dispatch admits both routes, produces two entries for one key, and the checkpoint never advances.

**Disposition: autofix.** Add to Domain naming (`:467`): "A domain is served by exactly one DAPR app-id per tenant (default: the domain name), registered once in the platform domain registry; a `(Domain, ProjectionType)` route is bound to exactly one app-id/version, and catalog refresh fails closed on a second binding."

### M2 - "Admission" names two different layers (medium)

AD-25's admission actor (`:400-458`) and the domain-service SDK's own `DomainServiceAdmissionContext` / `eventstore.domain.admission.stage` activity (`DomainService/DomainServiceRequestRouter.cs:31-115`) share a name but not a meaning. Suggest AD-25 state: "Only the EventStore admission actor is 'admission' for AD-5/AD-10/AD-12 purposes; domain-service pre-processing stages are validation and may not reserve, fence, or reply as admission."

### M3 - The fence carrier across the domain-service wire is unnamed (medium)

AD-25 allows "exactly the current non-zero fence" to cross "a domain-service ... boundary" (`:413-415`); the only fence type is the Server-internal `FencedCommandEnvelope(Command, IdempotencyExecutionContext)` (`Server/Actors/FencedCommandEnvelope.cs`), and `Contracts`/`DomainService` expose no fence member.
