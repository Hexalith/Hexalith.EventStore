# EventStore architecture technology and implementation review

**Verdict.** Three high-priority findings affect security and host interoperability. One medium-priority finding concerns the difference between current signing-key custody and the intended actor-context design. The Phase 4 readiness rejection remains warranted.

Reviewed November 21, 2026 against EventStore `df5dc226af69292b13dc0676e408e56081e0ff2a` and the working-tree spine with SHA-256 `7ad8fe0af4e9eb42903b3a2d08577b07eef21112f2a9f8a8a64fd01c15a921f6`. The committed Builds revision was `e303acd8` and the refreshed Builds checkout was `e1380b81`.

## Findings

1. **High · The OpenBao floor admits superseded security releases.** The stack table at architecture line 469 requires the October 1 floors of 2.7.1 and 2.6.4. Two October 26 high-severity advisories identify 2.7.2 and 2.6.5 as the first patched versions on those respective lines. Both November 19 releases, 2.7.3 and 2.6.6, carry further security fixes. The structural profile validator checks the declared and resolved versions against the October floors, so that check alone can accept a candidate missing the later fixes. Record the historical floors as such. Have Security and Platform qualify the candidate against current branch-specific advisories, bind the exact image and version, and reconcile the validator and its vectors before treating its result as sufficient. The currently unratified profile and blocked production gate contain this discrepancy. 2. **High · AD-28 understates the Development channel requirement.** Its rule at architecture line 380 limits the token requirement to non-Development endpoints. Frozen Story 5.14 lines 31 and 88 require an actual channel token in every environment. The shared verifier retains its environment flag for caller compatibility and refuses missing configuration. The Development framework-delivery test exercises this requirement. Two hosts could therefore conform to the current wording and disagree on whether a local channel with no token is admissible. Require the real receiver token on conforming Development hosts as well. Preserve the distinction between channel authentication and the separately scoped nonconforming issuer fixture. [Story 5.14](../../../../implementation-artifacts/spec-5-14-authenticated-fallback-and-dapr-framework-route-protection.md) · [Channel verifier](../../../../../src/Hexalith.EventStore.ServiceDefaults/Authentication/DaprAppChannelToken.cs) · [Host tests](../../../../../tests/Hexalith.EventStore.ServiceDefaults.Tests/HttpHostSecurityTests.cs)

3. **High · AD-16’s authenticated fallback omits unconditional refusal of unclassified endpoints.** Architecture line 261 describes an authenticated fallback. AD-28 rules out channel-only fallback admission but leaves other authenticated identities ambiguous. Story 5.14 lines 31, 39 and 87 require refusal before the handler for every credential on an unclassified route. ServiceDefaults gives the named human policy and the fallback distinct requirements at lines 41–44. Its host tests explicitly reject a human-policy fallback and cover late endpoint registration. Require each endpoint to carry an explicit classification, reserve the listed anonymous exceptions, and state that the fallback refuses every credential on unclassified endpoints. [Host security configuration](../../../../../src/Hexalith.EventStore.ServiceDefaults/Authentication/EventStoreHttpHostSecurityExtensions.cs) · [Endpoint inventory](../../../../../src/Hexalith.EventStore.ServiceDefaults/Authentication/EventStoreHttpEndpointInventory.cs) · [Host tests](../../../../../tests/Hexalith.EventStore.ServiceDefaults.Tests/HttpHostSecurityTests.cs) · [Story 5.14](../../../../implementation-artifacts/spec-5-14-authenticated-fallback-and-dapr-framework-route-protection.md)

4. **Medium · AD-24 blurs the current proof-key implementation and the dedicated-key target.** Its secret-contract paragraph at architecture line 326 says every internal proof uses dedicated keys and introduces the covered contexts as “today”. The status row at line 576 and the actual gateway, fenced context and erasure code show current use of the idempotency key ring. The November 1 owner decision separately accepted planning for a signing-capable HMAC erasure verifier, while AD-28 requires verification-only material for the proposed actor-context scheme. State which proof uses the ring today, which target recipients have verification-only material and which HMAC recipients are signing-capable. Bind custody migration and retirement proof to the relevant owner before authorizing a profile.
