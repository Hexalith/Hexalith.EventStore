High-priority findings

1. The credential rules reject an approved platform command

AD-18 and AD-36, lines 285–288 and 432. The sending and receiving rules allow a single credential kind. Story 2.14 records a narrowly scoped platform command that requires a workload assertion and separately validates the forwarded human identity against the bound subject. Implementations following the spine would reject this approved operation. Document the exact route and its two independent checks in the outbound, inbound and catalog rules. Preserve single-kind admission for ordinary operations. Story 2.14 · Command handler

2. A protected app channel needs the receiver token in Development

AD-28, line 380. The spine mandates token validation outside Development. The frozen Story 5.14 contract and the shared validator require a real receiver token on channel-protected routes in every environment. A Development host and its caller can therefore disagree before any business operation runs. Align AD-28 and the environment guidance with the shared validator and its Development tests. Story 5.14 · Channel validator

3. Authentication alone cannot authorize an unclassified endpoint

AD-16, line 261. “Authenticated fallback” admits an interpretation in which any signed-in user can reach a route lacking policy metadata. Story 5.14 and the installed fallback deny an unclassified endpoint for every caller. Specify that default explicitly, alongside named route policies and the enumerated anonymous exceptions. Verify the negative case with an authenticated caller. Story 5.14 acceptance cases · Host policy registration

4. The OpenBao floor predates published security fixes

AD-24/AD-26 stack entry, line 469. Both the spine and profile comparator accept the October floors of 2.7.1 and 2.6.4. Two October 26 advisories identify 2.7.2 and 2.6.5 as the first patched releases for those advisories. OpenBao published 2.7.3 and 2.6.6 on November 19. Security and Platform should review the supported branch and candidate, then align the spine and profile check with the approved floor. The production profile still requires ratification. Profile comparator · October advisory 1 · October advisory 2 · Release 2.7.3 · Release 2.6.6

5. The erasure verifier has conflicting key-custody rules

AD-24 and the Story 4.16 handoff, lines 326, 576 and 600. AD-24 assigns dedicated keys to internal proofs and includes the erasure capability. The approved Story 4.16 integration uses existing HMAC key generations and explicitly treats a verifier holding them as signing-capable. The two rules imply different trust and rotation boundaries. Name the present custody model, the approved 4.16 scope, and the transition to any future dedicated keys. Keep key distribution gated on qualification and owner-controlled migration. Story 4.16 approved integration

6. The assurance rule conflates required and achieved independence

AD-11 and the approval convention, lines 226 and 442. Roster size sets the required assurance level. Achieving independent approval also requires an authorized human whose numeric identity differs from the author’s. The 24-hour interval starts at the authenticated push to main that last changed the bound subject. “Last authored change” can be days earlier. State both checks in the common rule and have downstream records consume the achieved level. PRD assurance control · Approval window · Approver identity check

7. Release appears to depend on its own successor

AD-11, line 222. The final sentence asks for both release and deployment records and seals before either transition can pass. The evaluator checks the chain ending at the requested transition. Requiring the later promotion record would block a valid release. Specify separate inputs for each step. Release consumes its verified predecessor, release-owner record and applicable seal. Promotion subsequently consumes that release plus the qualified deployment, deployment-owner record and its own seal. Publication chain contract · Terminal-state check

8. Consumer removal crosses two distinct publication subjects

AD-11 and AD-22, lines 224 and 312. EventStore publishes a package and Platform promotes a separately composed host. AD-22’s “same immutable subject” wording can make a verifier reject that valid two-chain arrangement or apply a package receipt to a host. Specify how the promoted profile binds the exact package identity, how the host retains its own chain, and how a consumer-owner receipt binds the profile and the exact proposed removal. Subject ownership · Package-to-profile binding
