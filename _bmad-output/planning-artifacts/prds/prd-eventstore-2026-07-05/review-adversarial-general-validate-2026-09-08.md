# Adversarial Review — eventstore Phase 4 Implementation Readiness Recovery PRD

## Preamble

The document is polished and internally consistent at the sentence level, and that is the problem: it reads as a settled baseline while the repository it describes disagrees with it on the points that matter most. The PRD outsources its hardest requirement text to a hash of a document that is not in this repository, disclaims part of its own FR list as "historical", carries success metrics that were satisfied the day the file was created, and hides seven owner-deferred uncertainties behind an empty Open Questions section. The single biggest risk is NFR7: the PRD says append races "must be explicitly guarded or recovered", the only evidence collected records a silently lost durable write with no fence authorized and no story owning one, and every story in the chain is marked `done` — a new engineer reading this PRD plus `epics.md` would conclude append durability is delivered.

## Findings

- **[critical]** NFR7's append-race guard is marked delivered while the only evidence records silent data loss and no story owns a fix (§7 NFR7, line 276; §6.4 FR31, line 209; §11.2, line 427) — NFR7 requires that "append races ... must be explicitly guarded or recovered", and its coverage row lists 4.5 (`done` in `sprint-status.yaml:163`). FR31 requires only that remediation "must start with a live-sidecar two-writer race test ... before choosing an optimistic-concurrency fencing design" — a spike, not a guard. Story 4.5's own reconciliation in `epics.md:3112` reports the observed outcome `same-key-overwrite-raw-durable-write-lost`: "a raw same-sequence write was proven durable, then silently replaced by the accepted actor write without an exception or retry ... No fencing implementation is authorized by the partial evidence", the sealed packet "drifted from its bound source files, is not enforced by CI", and the AC at `epics.md:3149` says 4.5 "grants no authority to implement the fence". No FR, story, or `deferred-work.md` entry owns the fence. The same shape applies to FR24 (line 205): the requirement is to *renegotiate* sharding and update the spec; Story 4.6 is `done`; nothing owns implementing sharding. The PRD's own §6.4 "Done evidence" (line 211) is satisfied by tests that *observe* loss, not by loss being guarded. *Fix:* split NFR7 into one row per loss class (staged flush, stale pipeline, append race, committed-unpublished, duplicate side effects) each with an owning implementation story or an explicit "NOT delivered in Phase 4 MVP — deferred to `<story>`" marker; add an FR for the fencing implementation or state in §9.2 that append fencing is out of MVP scope; add the same for global-position sharding.

- **[critical]** The OQ8 authority order binds governance to a document that is not in this repository, has no path in the PRD, and overrides the PRD's own FR text (§1.1, lines 76-83) — "the Architecture + Security + Test-approved OQ8 design version 1.0.0 (SHA-256 `1a55b030…`) govern" and "Any pre-change FR27, NFR7, NFR16, or architecture wording is historical context only". No file in this repository hashes to that digest (checked the 2026-07-20 proposal, the 4.8 ledger, and the SPEC package). The 2026-07-20 proposal (`sprint-change-proposal-2026-07-20-oq8-durable-idempotency-admission.md:80-95`) locates it at `docs/exit-criteria/oq8-idempotency-design.md` in a *different* repository ("Folders"), noting "Both files are currently untracked in the Folders worktree". `epics.md:149` goes further: the design "override[s] historical FR27/NFR7/NFR16 text". So the document that §0 calls "the authoritative Phase 4 functional and non-functional requirements baseline" declares three of its own requirements non-authoritative in favour of an unlocatable external file, and `architecture.md:60-66` repeats the same deferral rather than owning it. "Folders" appears nowhere in the PRD. Circularity: `architecture.md:67-68` says for deployed-runtime parity "the final PRD updated 2026-08-16 govern[s]"; the PRD says `epics.md` "owns ... acceptance criteria"; `epics.md` says the external design overrides the PRD. *Fix:* name the repository, path, and commit of the governing design in §1.1; either project its normative content into FR27/NFR7/NFR16 (so the PRD is self-sufficient) or replace the "historical context only" disclaimer with a precise statement of which clauses are superseded and by what; add "Folders" and "Parties" to the glossary as external repositories with their roles.

- **[high]** Empty Open Questions and Assumptions Index launder seven owner-deferred uncertainties and one unlogged requirement rewrite (§12, lines 458-460; §13, lines 462-464; frontmatter `updated`, line 5) — "No PRD-level ownership or MVP-scope questions are open" and "No inline `[ASSUMPTION]` tags are present". The run memlog records deferrals the PRD reader never sees: clause-level completion evidence for omnibus FR26/FR33/FR34 (memlog line 23), finite bounds and production-path matrices for NFR5/NFR7/NFR8/NFR17 (line 24), correctness-gate binding and product-bet metrics (line 25), G5/goldens definitions (line 28), and the OCI/coordinated-slice items (lines 37-38). Separately, commit `8312bced` (2026-09-06) rewrote NFR3 and NFR4 (adding HS256-only, 60-second clock skew, non-empty asymmetric allowlist, "including clearly named Development configuration") with no memlog entry, and the frontmatter still says `updated: 2026-08-16`. The next day Story 5.3 — the *sole* NFR3 coverage (line 424) — flipped to `done` (`c83cc4c3`, 2026-09-07) while `epics.md:3810` still reads "Story 5.3 remains backlog ... committed Development configuration still carries fixed signing-key and administrator credential values" and `spec-5-3-…md:5` says `status: 'in-progress'`. Three artifacts, three states. *Fix:* populate §12 with each deferred item, its owner, and its due gate; add a memlog entry and bump `updated` for `8312bced`; reconcile 5.3's status across sprint-status, epics reconciliation, and spec before the PRD claims NFR3/NFR4 coverage.

- **[high]** SM1-SM3 cannot fail and no metric measures the product bet (§10, lines 355-357; §2, line 91) — SM1 "Implementation readiness re-run no longer reports missing PRD as a blocker" is satisfied by the file existing. SM2 "Every FR1-FR37 maps to at least one epic *and story* in `epics.md`" but §11.1 (lines 376-414) maps to epics only; only FR36/FR37 name stories, so the metric is not checkable from the PRD. SM3's deadline "before Phase 4 implementation resumes" elapsed months ago (Epics 1-3 are done), so it can never be re-measured. §2 states the bet: "Phase 4 succeeds only if platform reuse and operational hardening are delivered together" — no metric measures reuse (e.g. boilerplate removed from Tenants/Sample) or hardening (e.g. endpoints proven fail-closed), and the memlog (line 25) admits product-bet metrics were deferred. The counter-metrics are prohibitions, not measurements. *Fix:* add a story column to §11.1; retire SM1/SM3 as achieved; add thesis metrics with numbers — lines of platform plumbing deleted from Tenants (FR9), count of surfaces with a negative fail-closed test (NFR1), count of silent-loss classes with an owning implementation story (NFR7, currently not 100%).

- **[high]** A new engineer cannot tell FR36's real state from this PRD (§6.8 FR36 done evidence, line 254; §11.1, line 413; §11.3, line 442; SM6, line 363) — §11.1 calls FR36 "completed projection/query parity source/package closure in Story 1.20" and Epic 1 is `done`. But positive deployed-runtime parity is explicitly assigned to Story 3.15, whose packet holds 0 of 3 receipts and whose own verifier exits 1 ("exactly three packet-bound receipts are required", `sprint-change-proposal-2026-09-07.md`); the Epic 3 retrospective on 2026-09-07 is `verdict: rejected` and states "FR36 remains open". §11.3 says "Stories 1.20 and 3.12 remain `done` and are not reopened" and calls 1.20's evidence "immutable inputs", yet Story 1.21 (`epics.md:1329`) exists precisely to repair three drifted files in 1.20's "frozen" critical-evidence manifests — the PRD never mentions 1.21. Story 3.16 (`epics.md:2809`, added for FR19/FR21 maintenance) is also absent. *Fix:* add a per-FR status line for FR36 with three explicit sub-states — source/package (closed, 1.20), frozen-evidence integrity (repair pending, 1.21), deployed-runtime (open, 3.15 at 0/3) — and reference 3.16 under §6.3 or drop the §8.1 "latest validated compatible versions" constraint that only 3.16 implements.

- **[high]** Story identifiers collide across repositories and reused numbers, and SM4 cites IDs that now name different stories (§6.8, line 254; §9.2, line 337; §9.3, line 348; SM4, line 361; SM6, line 363) — "before Story 8.6 resumes" and "Story 8.11 blocks Parties Story 8.7 migration" use Parties story numbers, but EventStore Epic 8 has its own Story 8.6 (Azure Key Vault adapter, `epics.md:6382`) and Story 8.7 (Server persistence, `epics.md:6460`); FR36's done evidence names "Story 8.6" with no repository qualifier at all. "Stories 22.7a-d supplied prerequisites" is unexplained anywhere in the PRD. SM4 says "Oversized Stories 4.8, 7.14, and 8.2 ... are replaced by focused children", but 7.14 and 8.2 are live `backlog` stories under reused numbers (`story-id-migration-2026-08-01.md:43-60`), so a reader checking SM4 against `sprint-status.yaml` sees the "replaced" stories still pending. *Fix:* qualify every foreign story as `Parties 8.6`, `Parties 22.7a-d`; rewrite SM4 to say "former 4.8/7.14/8.2 umbrellas per `story-id-migration-2026-08-01.md`, now 4.9-4.15, 7.14/7.19/7.20, 8.2-8.11".

- **[medium]** Omnibus requirements let partial delivery read as complete (FR26, line 219; FR33, line 231; FR34, line 241; NFR16, line 285; NFR17, line 286; §11.2 NFR17 row, line 435) — FR34 bundles twelve independently failable obligations ("document at-least-once ... add poison/dead-letter ... bound in-memory deduplication ... normalize admin claims ... audit every state-mutating admin action ... hide deferred admin operations ... OpenBao ... DAPR Secrets API ... Kubernetes Secrets ... readiness/app-health ... restore meaningful IntegrationTests CI coverage"), all owned by Stories 7.1-7.10 which are entirely `backlog`, yet it shares one §6.7 "Done evidence" block with FR35, which is `done` (7.15-7.18). NFR17's coverage row lists 3.12 (`done`) alongside 5.6/7.6-7.9 (`backlog`); 3.12 satisfies only the "immutable image tags" clause, so a scan of the row shows green for a requirement whose core (`openbao`, `secretKeyRef`, default-deny) has zero implementation. FR26's nine clauses split across 5.1-5.3 (`done`) and 5.4 (`review`), with the Swagger gate, destructive CLI confirmation, ULID-safe correlation, and stale-doc clauses all in the un-done one. The memlog (line 23) explicitly deferred clause-level evidence. *Fix:* sub-letter the clauses (FR34a-l, NFR17a-g, FR26a-i) and give each its own coverage cell; do not let a `done` story appear in a row unless it closes a named clause.

- **[medium]** §6.1 "Done evidence" claims guardrails that are green by construction (§6.1, line 165) — "guardrails prevent domain modules from reintroducing reusable platform boilerplate" is asserted for a `done` epic. `epics.md:833` (Story 1.11 historical reconciliation) records "broad transitional host wiring and cross-file/computed route analysis remain explicit residual boundaries"; `deferred-work.md` DW-64 ("guardrails still cannot broadly ban all direct DAPR/host wiring"), DW-65 ("rely on lightweight same-file route resolution"), DW-77 ("evadable by a non-`*Dapr*`-named handler or a non-literal setter"), DW-78/79 (hard-coded 3-entry host list, `*.cs` only). A domain module that names its handler `RoutingHandler` and puts the route in a constant passes every guard. *Fix:* restate done evidence as a falsifiable negative control ("a fixture domain module that adds `AddDaprClient` in a non-`*Dapr*`-named class fails test X") and list the accepted evasions as residual risk in §12.

- **[medium]** "Production path" is load-bearing in FR36, NFR6, NFR8, and NFR16 but never defined, and the evidence accepted under it is fixture-instrumented (§4 glossary, lines 117-130; NFR16, line 285; FR36, line 252) — NFR16 demands "persisted ... evidence through their production paths" and "inspect production-path state"; FR36 demands proof "through production paths". Story 4.14's AC (`epics.md:3603`) accepts "deterministic time support is clearly labeled while durable PostgreSQL state and restart observations remain production-path proof", implemented via test-owned `Oq8FileTimeProvider`, `Oq8HostingStartup`, and `Oq8BoundaryCounterStartupFilter` injected into the host. Story 1.20's approved runtime is a proof package (`999.1.20-proof.fa2d1c9910f8`). Whether a startup filter, a file-backed clock, or a proof-suffixed package counts as "production path" is a judgment each story makes for itself. *Fix:* add a glossary entry that enumerates which layers must be real (OS process, DAPR sidecar, state component, actor placement, host pipeline) and which substitutions are permitted (time, external secrets, network) and require each packet to declare its substitutions against that list.

- **[medium]** The readiness gate in §1 is stated as a precondition but has no re-run trigger, and provenance stops at 2026-08-16 (§1, line 74; frontmatter `source_artifacts`, lines 7-52) — "Implementation should not resume as a full Phase 4 package until ... implementation readiness is re-run." The last re-run is `implementation-readiness-report-2026-08-01-post-correction.md` (`READY`). Since then: the 2026-08-16 proposal the PRD itself calls a "major-change proposal" (memlog line 46), the 2026-09-06 NFR rewrite, and a rejected Epic 3 retrospective — no re-run. `source_artifacts` omits seven approved proposals that exist on disk: `2026-08-01-story-3-11-operator-approval`, `2026-08-12` and `2026-08-12-story-3-13-step-3-gate`, `2026-08-14`, `2026-08-20` and `2026-08-20-commit-message-line-limits`, `2026-08-29`, `2026-09-07`, despite the memlog rule (line 35) that "approved proposals must be provenance-listed even when requirement text is unchanged". *Fix:* state the re-run trigger (any FR/NFR text change, any epic retrospective `rejected`); list the missing proposals; either re-run readiness or record in §12 that the 2026-08-01 READY verdict predates the current text.

- **[medium]** "Owner" approval is invoked fifteen times but the roles are never defined and, where recorded, the approver is the author (FR36, line 252; §6.8 done evidence, line 254; SM6, line 363; SM7, line 364; §11.3, lines 442-444) — the PRD requires "owner-reviewed", "explicit owner approval", "owner/security-approved", and "release-owner authority record" but names only "EventStore owner" (once) and "Product owners" (once) as roles; "release owner", "security owner", "evidence owner", and "Test Architect" appear in `epics.md` but not here. Story 1.20's approvals were "issued by `jpiquot` on 2026-08-01" (`epics.md:1285`), the same identity as the repository author and the "Administrator" who approves sprint changes. As written, "owner-approved" and "author-asserted" are indistinguishable, which is exactly the condition FR36 was created to prevent for consumers. *Fix:* define each owner role, state whether the same person may hold two of them for one packet, and require a non-authorship control (sealed validator run in CI, or a second identity) wherever the PRD says "owner-approved".

- **[low]** NFR18 requires documentation that does not exist and has no coverage row (NFR18, line 287; §11.2, lines 420-436) — "AOT/trimming is explicitly not a target ... and that constraint must be documented." No file under `README.md` or `docs/` mentions AOT, `PublishAot`, or trimming-as-a-target, and NFR18 is absent from the §11.2 table. *Fix:* name the target document path and add an NFR18 row.

- **[low]** Scope arithmetic and constraint drift (§9.1, line 325; §8.1, line 297) — "All seven Phase 4 epics currently listed in `epics.md`" while `epics.md` lists eight; the reader must infer that Epic 8 is the excluded one from §9.3. The §8.1 bullet "Keep the shared Builds catalog on the latest validated compatible versions ... never downgrade because search omits or unlists a package" is an operational policy with no FR and whose only implementer (Story 3.16) is unnamed in the PRD. *Fix:* "Epics 1-7"; either attach the catalog policy to FR21 or name 3.16.

- **[low]** Terminology is overloaded in ways that change what "done" means (§4, lines 117-130) — "parity" is used in eight senses in this document alone (query, package, deployed-runtime, topology, dual-provider, tenant-filter, posture, source/package), each with a different proof standard; "closure", "gate", "evidence" (byte-frozen packet vs passing test vs owner record), and "authority" are undefined. "Projection-Confirmed Success" is defined; "projection-backed provenance" (FR4, NFR8) is not, though it is the load-bearing distinction. *Fix:* add glossary entries for each parity kind with its proof standard, and for evidence/gate/closure/authority.
