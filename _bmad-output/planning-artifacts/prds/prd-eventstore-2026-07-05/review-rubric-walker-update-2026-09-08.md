# PRD Quality Review — eventstore Phase 4 Implementation Readiness Recovery (2026-09-08 update)

## Overall verdict

This update is a genuine, evidence-grounded improvement over the 2026-09-08 "Poor" baseline: the OQ8 authority now names a repository, path, commit and digest; NFR3/NFR4 got a real ratifying proposal that closes the provenance gap the prior review flagged as critical; FR36's Story 1.21/3.16 invisibility is fixed; and NFR7 was split into five named loss classes with per-class delivery state. Every traceability claim I spot-checked against `epics.md`, `sprint-status.yaml`, `deferred-work.md`, and `deploy/dapr/resiliency.yaml` held up exactly, including subtle en-dash range/footnote arithmetic in §11.2. But the rewrite left at least one new, load-bearing internal contradiction: §7 states NFR7 class (a) as settled ("guarded, owned by Story 5.1"), while §12's own OR3 says class (a)'s status "depend[s] on which source is correct" because Story 5.1 is `done` in the tracker but `backlog`/unverified in `epics.md` — the PRD contradicts itself two sections apart on a silent-data-loss guard. A broken sentence in NFR8, an unenforced glossary rule ("Owner Roles" non-authorship control), and one metric (SM12) without an enumerable denominator round out the substantive gaps. Grade: **Fair** — real repair work, but not yet safe to read any single section in isolation and trust it.

## Decision-readiness — adequate

Trade-offs are mostly named honestly and specifically: FR31/NFR7(c)'s "NOT delivered" framing names the exact evidence (`same-key-overwrite-raw-durable-write-lost`) and the unowned deferral (DW-326) rather than hiding it; §9.3's Epic 8 gating is stated as a real sequencing constraint, not softened. The `[Blocking]` markers in §12 (OR1–OR3) are used for genuine gate-openers, not safe checkpoints.

The exception is exactly what the task asked me to check: §7's NFR7 table asserts class (a) ("staged-state flush loss") is **guarded**, full stop — the same declarative register used for classes (b) and (d), which the evidence supports. But §12 OR3 (same document, same update) says the opposite in substance: Story 5.1 — the sole story backing class (a) — is `done` per `sprint-status.yaml` but its own `epics.md` body reads "Story 5.1 remains backlog... completion is not established," and OR3 explicitly states "NFR7 classes (a) and (c) depend on which source is correct." A reader who trusts §7 alone (as SM11 does — see below) walks away believing a silent-data-loss class is closed when the PRD's own §12 says it is not yet known which of two contradictory sources is true.

### Findings
- **critical** NFR7 class (a) contradicts §12 OR3 (§7, §12 OR3) — §7 declares "(a) staged-state flush loss - guarded, owned by Story 5.1" as settled fact. `_bmad-output/planning-artifacts/epics.md:3694-3708` (Story 5.1) says: "Story 5.1 remains backlog... completion is not established: [...] real-pipeline evidence has not proved the protected-endpoint/probe contract under Production configuration" (this text is actually the 5.1 body — see note below on exact wording) and `sprint-status.yaml:179` marks `5-1-infrastructure-failure-cache-clear: done`. §12 OR3 already names this exact contradiction and says class (a)'s truth is undetermined pending reconciliation. §7 should not state class (a) as delivered while §12 says its backing story's status is contested. *Fix:* qualify class (a) in §7 with the same hedge §11.2 uses generally ("declares coverage, not delivery — see OR3"), or resolve OR3 before asserting "guarded."
- **high** SM11 inherits the same overclaim (§10, SM11) — "Currently four of five" (only class (c) counted as unmet) assumes class (a) is genuinely guarded. If OR3 resolves against Story 5.1, the true count is three of five, not four. *Fix:* have SM11 read the count off OR3's outcome, or mark class (a) provisionally uncounted until OR3 closes.
- **low** §12's "No PRD-level ownership or MVP-scope questions are open" (§12 opening line) is a narrower, better-defended framing than the prior "no open questions" claim the earlier review criticized, since it is now backed by 9 explicit owner/trigger rows — but OR2/OR3/OR4 are all, in substance, ownership questions (who owns a contested story status, who owns DW-326). The distinction between "PRD-level ownership" and "story/requirement ownership" is real but not explained, and a skeptical reader will read it as the same evasion in new clothes. *Fix:* one sentence distinguishing "PRD scope/ownership" from "story-status reconciliation," or drop the opening claim and let the table speak for itself.

## Substance over theater — adequate

Most of the update is earned: DW-64/65/77/78/79 all exist verbatim as described in §6.1's done-evidence; the NFR17 resiliency policy names (`defaultRetry`, `pubsubRetryOutbound`, `pubsubRetryInbound`, `daprSidecar`, `pubsubTimeout`, `subscriberTimeout`, `defaultBreaker`, `pubsubBreaker`) match `deploy/dapr/resiliency.yaml` exactly, including the `statestore`/`pubsub` component split. The NFR3 rewrite is grounded in an actual code citation (`JwtBearerAuthenticationContract.cs:118-128`) via the ratification proposal. This is the opposite of boilerplate.

The one clear miss is new: the Glossary's **Owner Roles** entry (§4) asserts a cross-cutting governance rule — "wherever this PRD requires owner approval, the approval must be accompanied by a non-authorship control - a sealed validator run in CI, or a second identity. An approval issued by the author of the work it approves satisfies the record but not the control" — that is not applied anywhere else in the document. `epics.md` has a narrower, Story-8.11-specific version of this idea ("author self-approval... cannot close G5", line 6838), scoped only to G5. Nothing in §6.8 (FR36 owner approval for Story 1.20), §11.3 (release-owner authority record), or the Parity Packet definition invokes "non-authorship control." The glossary silently promotes a single story's anti-self-dealing clause into a PRD-wide requirement that no FR/NFR actually states or that any Done-evidence checks for.

### Findings
- **high** "Owner Roles" glossary overreach (§4, line 148) — defines a document-wide approval-integrity rule with no corresponding FR/NFR obligation and no other section that enforces or even references it. Downstream readers extracting "what does owner approval require" from the Glossary will apply a rule the rest of the PRD doesn't test for. *Fix:* either narrow the definition to describe the existing G5-specific rule (cite Story 8.11), or add the "non-authorship control" requirement to the Parity Packet definition / FR36 done-evidence / NFR text it's meant to govern.

## Done-ness clarity — thin

Most FRs still carry a testable Done-evidence clause, and the NFR7 per-class split materially improves this dimension over the prior version. Two new problems, both introduced by this update's rewrites:

### Findings
- **high** NFR8 broken sentence (§7, line 312) — the requirement reads: "...until that spec exists and is approved, no Epic 6 implementation story may start. must avoid unnecessary full-stream replay when projections are already current, and must expose projection freshness/version evidence..." The second sentence has lost its subject (a stray period splits what should be one clause list), so it's ambiguous whether the "avoid unnecessary full-stream replay" and "expose freshness/version evidence" obligations are gated by the same spec-approval precondition as the bounded-cost-model clause, or are freestanding requirements independent of Epic 6's spec gate. *Fix:* restore the subject, e.g. "...no Epic 6 implementation story may start. Runtime behavior must avoid unnecessary full-stream replay..."
- **medium** SM12 has no enumerable denominator (§10, line 413) — "Share of high-tier tests in the required evidence set that assert persisted state... Target: the full required set, per NFR16." Unlike SM10 (five named surfaces) and SM11 (five named loss classes), "the required evidence set" is not enumerated anywhere in NFR16 or elsewhere; NFR16 is prose ("erasure, batch recovery, handler idempotency, rebuild equivalence... durable-admission evidence...") without a fixed count. The section's framing ("Each is a count with a target, so it can fail") does not hold for SM12 as currently worded — there's no way to compute the share without first inventing the denominator. *Fix:* enumerate the required evidence set (even by test-suite name) or drop the "count" framing for SM12 specifically.
