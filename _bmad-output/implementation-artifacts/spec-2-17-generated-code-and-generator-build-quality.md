## Intent

**Problem:** NFR13/OR26 require the REST source-generator package and its generated controllers to build with zero warnings under warnings-as-errors and to follow EventStore code style, nullable, ULID and `ConfigureAwait(false)` rules. A bound CI command must fail on a seeded violation of each rule. Today the generator tests fail only on errors, and the generator project builds without code-style enforcement. Analyzers also skip `<auto-generated />` output. Style, CA2007 and Guid-parsing regressions in emitted code would therefore pass CI.

**Approach:** Keep emitter and generator behaviour unchanged: a probe on 2026-11-07 found zero violations. Add only the missing gates:
1. A `Generators.Tests` conformance class over representative fixtures. It fails on any warning in generated trees, a missing `#nullable enable`, an `await` without `.ConfigureAwait(false)`, or any `System.Guid` parse call. Each rule has a seeded-violation test.
2. `EnforceCodeStyleInBuild` on the generator project.
3. Repository style rules applied to generated output, using the mechanism chosen in Open Question 1.

The bound commands are CI's existing Release `-warnaserror` solution build and the `Generators.Tests` run.

## Boundaries & Constraints

**Always:**
- Reuse `RestApiGeneratorTestHarness` and the existing fixtures.
- Checks fail closed: zero generated sources or zero scanned awaits is a failure.
- Seeded violations mutate real generated text.
- If a gate exposes a real violation, fix the emitter, not the gate.
- Stage named paths only.

**Never:**
- Byte-stable or deterministic generator output.
- Emitter behaviour or public API changes beyond such fixes.
- Warning suppression, `NoWarn` or lowered severities.
- Repository-wide `EnforceCodeStyleInBuild`.
- Edits to Hexalith.Builds or CI workflows, or new CI lanes.
- Tenants host changes, BannedApiAnalyzers, new packages, or committed evidence.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Clean output | HappyPath + bound-query fixtures | No Warning+ diagnostic in generated trees; all rule checks pass | N/A |
| Seeded warning | Unused local injected into generated text | Warning check reports CS0168/CS0219 | Test names the diagnostic |
| Seeded nullable | `#nullable enable` removed | Directive check fails and CS8669 surfaces | Test names the file |
| Seeded await | One `.ConfigureAwait(false)` removed | Await check fails | Names the member |
| Seeded ULID | `Guid.TryParse(messageId, out _)` inserted | Guid check fails | Names the call |

## Open Questions

1. **How should code style be proven on the generated controllers?** Analyzers skip `<auto-generated />` files. Probes showed that Roslyn also ignores `generated_code = false` for source-generator trees, but honours it for copied files (CA2007 then fired).
   - **B: Conformance project (recommended).**
     - What changes: Sample.Api sets `EmitCompilerGeneratedFiles`. A new non-packable project, `samples/Hexalith.EventStore.Sample.Api.GeneratedCodeQuality`, copies Sample.Api's REST-generator files. It compiles them as ordinary code with `generated_code = false` and `EnforceCodeStyleInBuild`.
     - Gains: the real compiler, the real IDE and CA2007 analyzers, and the repository `.editorconfig`, all run inside CI's existing solution build.
     - Costs: one more slnx project, and the style seeding is a recorded local mutation rather than a permanent test.
   - **A: Analyzers inside the test.**
     - What changes: `Generators.Tests` loads the SDK's code-style and .NET analyzer DLLs and runs them over the generated text with the repository `.editorconfig`.
     - Gains: a permanent seeded test and no new project.
     - Costs: about 150 lines of option plumbing that has to mimic the build. The test breaks whenever the SDK's Roslyn version moves past the central `Microsoft.CodeAnalysis.CSharp` 5.9.0.
   - **C: Exempt generated output from IDE rules.** This follows the .NET convention for auto-generated code; style would be enforced on the generator package only. It is the cheapest option, but it departs from NFR13's "generated code must follow code style" and needs your acceptance.
