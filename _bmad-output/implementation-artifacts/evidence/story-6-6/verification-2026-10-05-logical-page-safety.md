# Story 6.6 logical-page and V1 consumer safety — 2026-10-05

Status: partial implementation evidence only. Story 6.6 remains in progress; no M1–M8 task or activation gate is closed by this record.

## Changes and current boundary

- `EventPublisher` checks the application-owned logical payload digest after unprotection and validates the whole addressed contiguous batch before sending its first event. It retains the complete version metadata tuple in the published envelope. This does not provide broker acceptance or signed membership evidence.
- A review repair now refuses any V2 or partial version tuple in the publisher's complete-batch preflight. A valid application digest alone cannot authorize publication before the qualified route proof exists. The dormant tuple-copying code remains for the later qualified path; this does not close M6.
- `ProjectionEventWireBuilder` validates the whole addressed contiguous batch before protection callbacks and checks each readable event's application digest before constructing handler input. Its legacy route continues to hold versioned events.
- `AggregateActor.GetEventsAsync` and `EventStreamReader.RehydrateAsync` refuse a legacy complete array over the approved 100,000-event, 64 MiB stored-payload and 256 MiB conservative event/metadata accounting ceilings. The check precedes list allocation and reads when count alone exceeds the ceiling. This is one stage of the required composed source/readable/working-memory plan, not complete B6 admission.
- `DaprLogicalEventReader.ReadPageAsync` offers an internal, actor-addressed Dapr logical page: at most 256 events, matching aggregate type, contiguous sequence, at most 128 MiB stored payload and 64 MiB effective payload, with actor metadata head/floor re-read and cleanup of resolved views on failure. The paired metadata reads are logical application observations, not provider attestation or independent committed-generation proof. No production consumer calls this method yet.
- `ProjectionUpdateOrchestrator` reads its checkpoint before history. It still reads full history and cannot assert the zero-read current path without projection-scoped verified head/checkpoint evidence.
- `AddEventStoreEventEvolutionManifestCandidate` now admits one explicit domain manifest into keyed DI only after its complete decoded topology and exact caller-supplied lower-case fingerprint validate. The registry owns each row, and duplicate domain registration fails. The candidate can run the existing supplied-graph G-row, reachability and file-hash check without claiming that the graph was captured from a trusted loader. No manifest is registered by the repository and no readiness or V2 route consumes this service.

## Exact missing M1/M2 prerequisite and code seam

`Client.Events.EventDomainRegistry` and `EventLogicalViewResolver` are internal local kernels. The new `AddEventStoreEventEvolutionManifestCandidate` registration seam has no supplied domain rows or authoritative gateway capability pin in this repository and advertises no readiness. Its `RequireSuppliedLocalClosure` method reaches `EventDependencyClosureVerifier`, which verifies a supplied graph but does not capture/lock the actual managed/native loader or prove complete handler/catalog roots. The missing authority input is a per-domain exact D/V/A/E/F/S/G manifest, gateway-signed/pinned fingerprint, and the complete executing dependency graph and roots from a trusted loader and handler catalog; a caller-produced matching fingerprint or graph is insufficient. There is no production `IEventEvolutionReader` service or purpose-01 signed route/page claim and verifier binding the Dapr logical page to a handler. `Server.Events.DaprLogicalEventReader` remains actor-local and unregistered. `DomainServiceRequestRouter.ProcessAsync` rejects `WriterMode`, `CommandStateProof` and `VerifiedEffectiveEvents`; `DaprDomainServiceInvoker` admits only implicit V1 responses; `AggregateActor`/projection typed reads continue to fence versioned history. Wiring an effective payload directly into these legacy consumers would bypass the signed route/complete-prefix and handler compatibility checks required by the spec, so this page API remains dormant.

The selected production profile path `deploy/dapr/production-profile.yaml` is absent and AD-26 remains unratified. The owner confirmed on 2026-10-05 that no approved production profile exists yet. The local AppHost started for baseline inspection, but its `security` resource was unhealthy and dependent services waited; it was stopped before builds. No live Dapr component, two-host crash, mixed-fleet, carrier, package/API/wire consumer, or provider capability gate is claimed here. V2 writes and proof-dependent operations remain fenced.
